🔴 КРИТИЧЕСКИЕ АРХИТЕКТУРНЫЕ ПРАВИЛА (НАРУШЕНИЕ = ОТКАЗ)

ЗАПРЕТ НА НОВЫЕ MonoBehaviour: WorldProceduralScatterDirector остается ЕДИНСТВЕННЫМ компонентом на сцене. Запрещено разбивать его на независимые скрипты с собственными Update() или SlowTick(). Директор должен стать координатором, вызывающим сервисы и утилиты строго по очереди.

СТРОГИЙ ZERO-GC (Tick & Hot Paths):

Никакого LINQ (.Where, .Select, .FirstOrDefault и т.д.).

Только классические циклы for (int i = 0; i < count; i++). Использование foreach допускается только со структурами-энумераторами (напр. Dictionary<K,V>.Enumerator) во избежание boxing'а.

Никаких замыканий (Closures/Lambdas) в сортировках. Использовать IComparable<T> у структур.

Конкатенация строк и интерполяция ($"") строго обернуты в #if UNITY_EDITOR || DEVELOPMENT_BUILD.

БЕЗОПАСНОСТЬ СЕРИАЛИЗАЦИИ: Не трогать инспектор. Все [SerializeField] (префабы, настройки, менеджеры) остаются в Директоре. При изменении имени переменной ОБЯЗАТЕЛЬНО использовать [FormerlySerializedAs("OldName")].

🛠 АНАЛИЗ ПРОБЛЕМ И ПЛАН РЕФАКТОРИНГА
Проблема 1: Остановка главного потока (Job Stall)

Анализ: Сейчас ScheduleCellSamplingJob и Complete() вызываются подряд в одном методе RebuildScatterPreview. Это убивает смысл Job System — главный поток замораживается в ожидании воркеров.

Решение: Разрезать пайплайн SlowTick на стейт-машину, работающую в разные кадры:

Tick 1 (ScatterState.Sampling): Заполняем _cellSamplingInputs, делаем Schedule(), сохраняем JobHandle, выходим.

Tick 2 (ScatterState.Processing): Делаем Complete(), читаем данные _cellSamplingOutputs, запускаем расчет бюджетов и спавн.

Проблема 2: Линейный поиск O(N) в кэше кандидатов

Анализ: Структура CandidateMap использует for-цикл по массиву для поиска ключей. При 512 элементах это вызывает экспоненциальный спайк CPU.

Решение: Реализовать FastCandidateMap (Linear Probing Hash Map).

Поиск и вставка за O(1). Без использования System.Collections.Generic.Dictionary.

Использовать 3 массива: ScatterCandidate[] values, long[] keys, int[] buckets.

Правило COLD ALLOC: Массивы выделяются один раз в Init(capacity).

Запрет Array.Resize: При превышении capacity в рантайме новые кандидаты отбрасываются (Fail-Safe), пишется Warning (только в Dev сборке), аллокации запрещены.

Проблема 3: Параметрический ад (Методы с 30+ аргументами)

Анализ: Методы (например, InjectRescuePlacementsIfNeeded) прокидывают десятки ссылок на массивы и словари, убивая процессорный кэш (Stack Abuse).

Решение: Использовать паттерн Parameter Context.

Создать структуру public ref struct ScatterRescueContext.

ref struct гарантирует размещение только на стеке (0 аллокаций в куче).

Заменить передачу массивов внутри контекста на Span<T>.

Проблема 4: Смешение логики (God Object)

Анализ: Директор самплит, считает математику биомов, общается с GPU Instancer и пулами.

Решение (Data-Oriented Split): Вынести функционал в 4 независимые сущности (файлы):

ScatterWorkingMemory (Данные): Класс/структура, хранящая ВСЕ коллекции (List, Dictionary, NativeArray). ОБЯЗАНА реализовывать IDisposable. Директор должен вызывать Dispose() в OnDestroy, чтобы избежать Native Memory Leaks (C++ утечек).

ScatterHeuristicsUtility (Чистая математика): public static класс. Перенести туда все switch-конструкции, вычисления Heat, Score, GetPatternHeatScale, GetDepthDomainScale. Не имеет состояния (Pure Functions).

FloraGPUInstancingService & ScatterSpawningService (Исполнители): Вынести логику _floraGpuiMatrices, FlushFloraGpuiBuffers и ObjectPoolManager. Директор только передает им команды.

ScatterDiagnosticsTracker (Отладка): Вынести 100+ полей _debug.... Код должен существовать только внутри #if UNITY_EDITOR || DEVELOPMENT_BUILD.
4. БЕЗОПАСНОСТЬ JOB SYSTEM (CRITICAL):
Разделяя Schedule() и Complete() на разные тики, ОБЯЗАТЕЛЬНО введи защиту от конкурентного доступа. Добавь поле bool _isSamplingJobRunning. Пока джоба выполняется, метод SlowTick должен делать return. Запрещено трогать NativeArray, пока не вызван Complete().
5. ЖИЗНЕННЫЙ ЦИКЛ ref struct (CRITICAL):
ScatterRescueContext — это ref struct. Его нельзя сохранять в поля класса и передавать между кадрами. Контекст должен создаваться СТРОГО во второй фазе стейт-машины (ScatterState.Processing), сразу после вызова Complete() для Job'ы.


В методе OnDisable или OnDestroy, ПЕРЕД вызовом _memory.Dispose(), Директор ОБЯЗАН принудительно дождаться завершения джобы: samplingHandle.Complete();. Только после этого можно освобождать Native-память.

При переносе логики отрисовки в FloraGPUInstancingService, ЗАПРЕЩЕНО менять тип буфера Matrix4x4[] на List или NativeArray. Оставь ручной ресайз через Array.Copy. Это жесткое требование API плагина GPUInstancer.

СТРОЖАЙШЕ ЗАПРЕЩЕНО изменять логику, константы и битовые сдвиги внутри StableRandom01, ComputeStableHash, ComputeRuleIdHash и ComposeKey. Они должны быть перенесены "как есть" (байт в байт), чтобы сохранить математическую детерминированность сгенерированных миров.
Создай структуру SamplingSnapshot. В Кадре 1 запиши туда CenterCellX, CenterCellZ и PlayerPosition. Передай этот Snapshot во вторую фазу (Processing). Все расчеты дистанций и выборки ячеек в фазе Processing ОБЯЗАНЫ использовать данные из Snapshot, а не актуальный playerTransform.position. Это гарантирует математическую целостность генерации.
В ScatterSpawningService должен быть жесткий лимит на количество операций в одном кадре (используй существующие maxInitialScatterCreatesPerRebuild и maxPoolWarmupPerRebuild). Если объектов больше, сервис должен уметь "доспавнивать" их в следующих тиках SlowTick, не блокируя основной поток.

Все переменные с атрибутом [SerializeField] и [Header] ОБЯЗАНЫ остаться в файле WorldProceduralScatterDirector.cs. Новые сервисы и классы должны получать эти значения через конструктор или метод Init(). Директор — владелец настроек, Сервисы — их потребители.

Метод проверки proceduralStateRegistry.IsPlacementSuppressed(key) является блокирующим. Его нельзя выносить в асинхронные Jobs (так как реестр — это managed-объект). Проверка должна происходить строго в фазе Processing ПЕРЕД добавлением кандидата в список _desiredPlacements. Ни один объект, помеченный как «собранный» в WorldProceduralStateRegistry, не должен попасть в финальный список спавна.
При рефакторинге логики HasLayerBudget и CanAcceptCandidate, учитывай параметр fieldSample.caveProximity и fieldSample.seafloorHeight. Система должна поддерживать «многоэтажность» в пределах одной XZ-ячейки, если это предусмотрено данными сэмплера. Не допускай логики, которая считает, что в одной ячейке сетки может быть только одна «высота».
В ScatterSpawningService введи систему приоритетов. Сначала спавнятся объекты с family.expectsInteraction == true (ресурсы, квестовые предметы), и только потом — декоративная флора (трава, кораллы). Декорации могут подождать следующего кадра, ресурсы — нет.

🚨 ПРЕДУПРЕЖДЕНИЕ ПО ИНТЕГРАЦИИ NARRATIVE AI (Atlas-6)

Архитектурный аудит новой системы лорного ИИ (Narrative AI) выявил 3 критических риска. Их необходимо учитывать при работе со смежными системами:

O(N) Nearest Search (Убийца фреймрейта): GetNearestUndiscoveredPOI не должен делать линейный перебор Vector3.SqrMagnitude(player, poi) по всем 500+ объектам карты.

Решение: ИИ обязан использовать Spatial Partitioning. Использовать существующую сетку чанков Scatter'а (_gridPlacements), опрашивая только соседние ячейки через ComposeScatterGridKey(playerX, playerZ).

Навигация сквозь стены: Поиск по радиусу может выбрать объект за 10 метров за стеной пещеры, хотя реальный путь до него 500 метров.

Решение: Базовый поиск отбирает топ-3 точки по дистанции, финальный выбор делается через асинхронный NavMesh.CalculatePath (или A*), чтобы убедиться в наличии проходимого пути.

Утечки памяти (Memory Leaks): Если POI подписывается на NarrativeEvents, но выгружается из памяти без вызова OnDisable (краш или пул), статичный ивент удержит ссылку в памяти.

Решение: Использовать интерфейс реестра (Registry) или паттерн IObserver вместо static event.
