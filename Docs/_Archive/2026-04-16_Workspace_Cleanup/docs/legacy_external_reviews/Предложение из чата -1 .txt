🔬 Почему нейросеть всегда будет писать "правильно, но скучно"?

Нейросети тренированы на средних текстах со всего интернета и предсказывают наиболее вероятное следующее слово. А хороший сюжет — это то, что маловероятно, но логично. Именно этот разрыв рождает скучные клише и ощущение фальши. Ты не один такой, все с этим сталкиваются.

🧠 Как делать сюжет, который не "воняет нейросетью" (конкретные техники)

1. "Конструктор" из старых фрагментов (Техника Frankentext): Заставь ИИ собирать рассказ как "Франкенштейна" — из кусочков, которые ты сам написал. Выдай нейросети задание: взять твои "мясо", "исследование" и "сюжетный поворот" и сшить их в одну историю. Исследования показывают, что такой метод делает текст более живым и его сложнее распознать как ИИ-генерацию, так как модель выступает не автором, а композитором.

2. Режиссура от ИИ: не пиши, а управляй (Многоагентная система): Вместо одного сценариста используй целую команду агентов. Один придумывает глобальный план, второй с командой ИИ-актеров разыгрывает сцены, третий всё это переписывает в связный текст. Это создает более глубоких персонажей и логичный сюжет.

3. "Буря мозгов" с десятикратным запасом (Техника NarrativeLoom): Этот метод копирует природу — сначала генерируй много вариантов, потом отбирай лучшие. Одновременно запускай 10 разных ИИ-личностей: "пост-апокалипсис", "нуар", "хоррор" и т.д. Ты получаешь 10 совершенно разных идей, выбираешь лучшую и дорабатываешь. Так ты борешься с главной проблемой нейросетей — "вероятностной ловушкой", которая толкает их к банальностям.

4. Песочница для сюжета (Фреймворк WhatELSE): Это инструмент, который позволяет загрузить в ИИ несколько примеров хороших историй, и на их основе ИИ строит "карту возможных сюжетов". Ты видишь, куда могут привести разные выборы игрока, и можешь вручную подрезать или расширить границы. Это даёт тебе контроль над пространством сценария, не убивая его динамику.

5. Подрезание крыльев генерации (Анти-Слоп Техники): Нейросети обожают слова-паразиты вроде "Delve", "Certainly", "a profound sense". Фреймворк "Antislop" может отлавливать и вырезать их на лету прямо во время генерации.

## 🔥 БЛОК 1: PATH TO CORECLR (Unity 6.8) — КРИТИЧНО

### Суть изменения
- **Mono будет полностью удалён** в Unity 6.8 (планируется к 2026 году)
- Переход на **CoreCLR** (.NET modern runtime) — это фундаментальное изменение архитектуры скриптинга
- Требуется подготовка кодовой базы заранее

### Ключевые технические детали из обсуждения:
1. **Проблема с удержанием ссылок в коллекциях**:
   - Контейнеры (List, Dictionary и т.д.) **удерживают ссылки** на объекты
   - При плохой практике кодирования (например, ручное управление `_count` без очистки ссылок) сборщик мусора не может освободить память
   - В новой модели AssemblyLoadContext это может **блокировать перезагрузку ассембли**

2. **Что происходит при утечке Assembly**:
   - Unity планирует **отчитываться пользователю** о случаях, когда AssemblyLoadContext "утёк"
   - Возможен сценарий, когда в памяти будут **две версии типов** из одной ассембли — старая (не выгруженная) и новая
   - Новые инстансы будут использовать новую ассемблю, но старые объекты останутся со старой логикой

3. **Fast Enter Play Mode**:
   - Опция "Domain Reload" будет принудительно отключена при переходе на CoreCLR
   - **"Scene Reload" скорее всего останется**, но потребует рефакторинга кода, не зависящего от доменной перезагрузки

4. **OverflowException**:
   - В CoreCLR поведение арифметических переполнений может измениться
   - Пример: `int i = int.MaxValue + 1` теперь может выбрасывать `OverflowException` в проверяемом контексте
   - Нужно аудитировать критичную арифметику

### Что делать сейчас:
- Прочитать официальное руководство: [Path to CoreCLR, 2026: Upgrade Guide](https://discussions.unity.com/t/path-to-coreclr-2026-upgrade-guide/1714279)
- Проверить код на:
  - Ручное управление памятью через `_count` и подобные паттерны
  - Статические коллекции, которые никогда не очищаются
  - События, на которые подписываются, но не отписываются
- Протестировать проект с включённой опцией "Domain Reload = false" в Editor

## 🧠 БЛОК 2: ОПТИМИЗАЦИЯ ПАМЯТИ ДЛЯ ПРОЦЕДУРНЫХ МИРОВ

### Основные паттерны проблем (из статьи Bhavisha Bhogayata):

#### 1. "Память не освобождается сама"
- **Проблема**: Генерация текстур/спрайтов в runtime без явного уничтожения
- **Симптом**: Постепенный рост потребления памяти → краши на устройствах с 1 ГБ ОЗУ
- **Решение**:
```csharp
Destroy(texture);
Destroy(sprite);
Resources.UnloadUnusedAssets();
System.GC.Collect();
```
- **Вывод**: Если аллоцируете вне чистого managed-кода — управляйте жизненным циклом вручную

#### 2. Скрытые аллокации в Update-циклах
- **Проблема**: Создание объектов каждый кадр
```csharp
void Update()
{
    var tempList = new List<int>(); // аллокация каждый кадр!
    var message = "Score: " + score; // строковая конкатенация = новая строка
}
```
- **Последствие**: При 60 FPS даже мелкие аллокации создают постоянное давление на GC → фрейм-дропы
- **Решение**:
  - Переиспользовать объекты (пулинг)
  - Избегать конкатенации строк в Update
  - Использовать интерполяцию: `$"Score: {score}"` вместо `"Score: " + score`

#### 3. Event listeners, которые никогда не отписываются
- **Проблема**: Объект уничтожен, но событие всё ещё держит на него ссылку
```csharp
// Подписка
eventManager.OnUpdate += MyHandler;
// Забыли отписаться при уничтожении → утечка
```
- **Решение**: Всегда отписываться в `OnDestroy()` или `OnDisable()`
```csharp
eventManager.OnUpdate -= MyHandler;
```

#### 4. Тестирование только на высокопроизводительных устройствах
- **Проблема**: На ПК с 32 ГБ ОЗУ проблемы не видны, но на мобильном устройстве с 1 ГБ — краши
- **Решение**: Обязательно тестировать на минимально поддерживаемых устройствах

## ⚙️ БЛОК 3: MonoBehaviour vs C# Class vs Struct — Детальное сравнение памяти и производительности

### Тестовый объект "Actor" с полями:
```csharp
public string actorName;
public string actorTag;
public string currentState;
public bool isStunned, isOnFire, isFrozen, isPoisoned, isDead;
public float currentHealth, maxHealth;
```

### Результаты замеров памяти (1000 экземпляров):

| Метрика | MonoBehaviour Actor | Plain C# Class | C# Struct |
|---------|-------------------|----------------|-----------|
| Тип | Unity object | C# reference type | C# value type |
| Создание | `Instantiate()` | `new` | `new` в массиве |
| Расположение | Native + Managed heap | Managed heap | Inline в массиве (heap) |
| Память на объект | ~2.8 KB | ~56 B (данные) / ~164 B (с данными) | Inline, нет отдельных объектов |
| 1000 объектов | ~1.14 MB | ~55 KB / ~85 KB | ~39 KB (без строк) / ~144 KB (со строками) |
| Количество аллокаций | 1000 отдельных объектов | 1000 отдельных объектов | 1 аллокация массива |

### Ключевые выводы:
1. **MonoBehaviour — самый тяжёлый**: каждый экземпляр — это GameObject + Transform + MonoBehaviour + синхронизация native/managed
2. **Plain C# class в 20× легче** MonoBehaviour, но всё ещё создаёт 1000 отдельных объектов на heap
3. **Struct не экономит память сам по себе**, но:
   - Данные хранятся **непрерывным блоком** в памяти → лучше кэш-локальность
   - Одна аллокация массива вместо 1000 → меньше фрагментации heap
   - Быстрее итерация в циклах (CPU prefetch)

### Важное предостережение про struct:
```csharp
// ОШИБКА: передача struct по значению в метод
private void UpdateActor(ActorStruct actor) // копирует весь struct!
{
    actor.currentHealth += 1f; // меняет копию, оригинал не затрагивается
}

// ПРАВИЛЬНО: передача по ссылке
private void UpdateActor(ref ActorStruct actor)
{
    actor.currentHealth += 1f; // меняет оригинал
}
```

### Когда что использовать:
- **MonoBehaviour**: только когда нужен GameObject в сцене, сериализация в Inspector, Unity-события
- **C# class**: бизнес-логика, данные, которые не требуют Unity-компонентов
- **struct**: массивы данных для частой итерации, ECS-стиль, когда важна кэш-локальность

## 🗜️ БЛОК 4: УМЕНЬШЕНИЕ РАЗМЕРА БИЛДА (Unity 6.3+)

### Отключение физического движка
- **Зачем**: Если игра не использует физику (2D пазл, визуальная новелла, UI-приложение)
- **Экономия**: 10-15 МБ для WebGL / mobile билдов
- **Как**: Project Settings → Player → Global Settings → Optimization → Physics Runtime → **None**

### Что это даёт:
1. **Уменьшение размера билда**: удаляются PhysX (3D) или Box2D (2D) нативные библиотеки
2. **Снижение нагрузки на CPU**: не выполняется внутренний цикл FixedUpdate физики
3. **Экономия памяти**: не аллоцируются буферы для коллизий, broad-phase, solver

### Альтернатива для простой логики:
```csharp

    }
    
    // Оптимизация: избегать sqrt
    // if ((pos1 - pos2).sqrMagnitude < dist * dist)
```

## 🧩 БЛОК 5: ECS КАК ПАКЕТ ПО УМОЛЧАНИЮ (Unity 6.4)

### Контекст:
- С Unity 6.4 ECS (Entity Component System) включён в стандартную поставку
- Процедурная генерация с `WorldProceduralScatterDirector` — идеальный кандидат для ECS

### Практический опыт использования leoecs-lite (из блога Ariel Coppes):

#### Архитектура "Controllers" как скриптовый слой:
```csharp
public class RepairDroneController : MonoBehaviour, IUpdate, IStateChanged, IInit
{
    public float healingPerSecond = 1;
    public float totalHealing;
    private float currentHealing; // ← RUNTIME данные — проблема!
    
    public void OnUpdate(World world, Entity entity, float dt)
    {
        // Доступ к компонентам через entity.Get<>()
        ref var states = ref entity.Get<StatesComponent>();
        // Логика...
    }
}
```

#### Критически важный принцип: **Stateless Controllers**
- **Проблема**: Хранение runtime-данных (`currentHealing`, `rayEntity`) прямо в Controller
- **Последствия**:
  - Данные не доступны другим системам
  - Сложнее отлаживать (нет единой структуры)
  - Нельзя переиспользовать инстанс Controller'а для нескольких сущностей
  - Сложнее сериализовать для save/load или сети

- **Решение**: Выносить runtime-данные в отдельные компоненты:
```csharp
public class RepairDroneComponent : IEntityComponent 
{
    public float currentHealing;
    public Entity rayEntity;
}
// Использовать: entity.Get<RepairDroneComponent>()
```

#### Система конфигураций (опыт Iron Marines Invasion):
- JSON-файлы с иерархической структурой:
```json
{
  "army.units.unit_ranger": {
    "health": 100,
    "abilities.base_attack.damage": 100
  }
}
```
- `ConfigurationComponent` хранит ключ и кэшированный Dictionary
- `ConfigurationSystem` парсит JSON и заполняет компоненты
- **Преимущество**: дизайнеры могут балансировать без перекомпиляции кода

#### Система апгрейдов через overrides:
```json
{
  "upgrade_super_rangers": {
    "army.units.unit_ranger": {
      "healthPercentage": [120, 140, 160, 200]
    }
  }
}
```
- Апгрейды переопределяют значения в основном словаре конфигураций
- Поддержка процентов и множителей

#### Реакция на события через Event-компоненты:
```csharp
// Вместо хранения previousState в HealthComponent:

        var eventData = e.Get<HealthStateEventComponent>();

```

- Позволяет фильтровать сущности по компонентам
- Поддержка кастомных инспекторов для сложных компонентов

## 🎨 БЛОК 6: RENDER GRAPH VIEWER (Unity 6.4)

### Что такое Render Graph:
- API для доступа к рендер-пайплайну на любом этапе кадра
- Автоматическая оптимизация: слияние пассов, управление ресурсами
- Безопасный доступ к ресурсам рендеринга

### Render Graph Viewer: окно анализа
- **Расположение**: Window → Analysis → Render Graph Viewer
- **Структура**:
  - Верхняя строка: рендер-пассы в порядке выполнения
  - Левый столбец: ресурсы в порядке создания
  - Сетка: цветные блоки доступа (Read/Write/Load/Store)

### Цветовая кодировка блоков:
| Цвет | Значение |
|------|----------|
| 🔴 Красный | Запись (Write) |
| 🟢 Зелёный | Чтение (Read) |
| 🔵 Синий угол | Очистка при загрузке (Clear on Load) |

## 📦 БЛОК 7: ADDRESSABLES ДЛЯ БОЛЬШИХ МИРОВ

### Часть 1: Основы и локальные адресаблы

#### Ключевое отличие от стандартного подхода:
| Стандарт Unity | Addressables |
|---------------|--------------|
| `Instantiate()` загружает префаб в память при старте сцены | `Addressables.LoadAsync()` загружает по требованию |
| `Destroy()` удаляет инстанс, но "чертёж" остаётся в ОЗУ | `Addressables.ReleaseInstance()` полностью выгружает ресурс |
| Все ассеты в памяти с начала | Только нужные ассеты в памяти в нужный момент |

#### Базовая настройка:
1. Установить пакет Addressables через Package Manager
2. Отметить ассет как "Addressable" в Inspector
3. Использовать `AssetReference` и `AsyncOperationHandle`:
```csharp
[SerializeField] private AssetReference _player;
private AsyncOperationHandle<GameObject> _playerReceipt;

void Start()
{
    _playerReceipt = _player.InstantiateAsync();
}

void Cleanup()
{
    if (_playerReceipt.IsValid())
        Addressables.ReleaseInstance(_playerReceipt);
}
```

#### Преимущества:
- **Управление памятью**: явный контроль загрузки/выгрузки
- **Живые обновления**: возможность загружать контент с сервера без обновления приложения
- **Ускорение билдов**: разделение кода и контента → быстрее итерации в CI/CD

### Часть 2: Удалённые адресаблы + Unity Cloud Content Delivery (CCD)

#### Сценарий: 3-этажное здание, загрузка этажей "на лету"

#### Настройка Remote Addressables:
1. **В AddressableAssetSettings**:
   - Включить "Build Remote Catalog"
   - Установить "Build & Load Paths" → "Remote"

2. **Настройка профилей** (Window → Asset Management → Addressables → Profiles):
   - `Remote.BuildPath`: оставить по умолчанию (`ServerData/[BuildTarget]`)
   - `Remote.LoadPath`: вставить URL из Unity Cloud Dashboard

3. **Настройка групп ассетов**:
   - Выбрать группу с префабами этажей
   - Установить:
     - Build Path → `<Remote.BuildPath>`
     - Load Path → `<Remote.LoadPath>`
   - **Критично**: Advanced Options → Bundle Mode → **"Pack Separately"**
     - Без этого все этажи упакуется в один файл → игрок скачает всё сразу

#### Настройка Unity Cloud Content Delivery:
1. В [Unity Cloud Dashboard](https://cloud.unity.com) → Cloud Content Delivery
2. Создать Bucket (например, `RemoteFloorsBucket`)
3. Сбилдить адресаблы: Addressables Groups → Build → New Build → Default Build Script
4. Загрузить содержимое папки `ServerData/[Platform]` в Bucket через веб-интерфейс
5. Создать Release в Dashboard
6. Скопировать полученный URL в `Remote.LoadPath` в Unity

#### Логика загрузки в runtime:
```csharp
public class AddressableManager : MonoBehaviour
{
    [SerializeField] private IntEventChannelSO onFloorSelected;
    [SerializeField] private AssetReference[] floorReferences;
    private AsyncOperationHandle<GameObject> _currentFloorReceipt;
    
    private void LoadFloor(int floorIndex)
    {
        // Выгрузить текущий этаж из памяти
        if (_currentFloorReceipt.IsValid())
            Addressables.ReleaseInstance(_currentFloorReceipt);
        
        // Загрузить новый
        _currentFloorReceipt = floorReferences[floorIndex].InstantiateAsync();
    }
}
```

#### Кэширование:
- После первой загрузки ассеты **автоматически кэшируются локально**
- Последующие загрузки берутся с диска, а не из сети

#### Тестирование в Editor:
- По умолчанию Play Mode использует "Asset Database (fastest)" → пропускает сеть
- Для тестирования реального поведения: изменить на **"Use Existing Build"**

#### Сравнение Pack Together vs Pack Separately:
| Режим | Поведение | Когда использовать |
|-------|-----------|-------------------|
| Pack Together | Все ассеты группы в одном файле | Маленькие ассеты, всегда нужны вместе |
| **Pack Separately** | Каждый ассет — отдельный файл | Большие уровни, загрузка по требованию |

## 🎮 БЛОК 8: ФИЗИКА НА ГПУ — ПРОЕКТ «MOLECULES»

### Суть проекта
Репозиторий: [github.com/JohannHotzel/Molecules](https://github.com/JohannHotzel/Molecules)

Это **полностью вычислительная физическая система**, работающая на видеокарте через Compute Shaders. Не использует встроенный PhysX/Box2D Unity.

### Ключевые возможности:
1. **XPBD (Extended Position Based Dynamics)** — современный метод решения ограничений, стабильнее классического PBD
2. **Spatial Hash Collisions** — хэш-пространство для быстрого поиска коллизий без перебора всех пар
3. **Mesh Voxelization** — вокселизация мешей для точных коллизий сложных форм
4. **Coulomb Friction** — модель сухого трения Кулона для реалистичного скольжения
5. **Breakable Constraints** — возможность «разрыва» связей между частицами при превышении нагрузки

### Для чего это может быть полезно в процедурном мире:
- Симуляция тысяч/миллионов частиц (песок, снег, пепел, магические эффекты)
- Динамическое разрушение ландшафта без дорогих вычислений на CPU
- Взаимодействие игрока с «живой» средой (например, следы на снегу, которые реально деформируются)

### Технические ограничения:
- Требует поддержки Compute Shaders (не все мобильные устройства)
- Нет встроенной интеграции с Unity Physics — нужно писать свой слой взаимодействия
- Отладка сложнее: данные живут на GPU, нужно выгружать их для инспекции

### Пример архитектуры взаимодействия:
```csharp
// 1. Инициализация симуляции на GPU
public class GPUPhysicsSimulator : MonoBehaviour
{
    public ComputeShader simulationShader;
    public int maxParticles = 100000;
    
    private ComputeBuffer particleBuffer;
    private ComputeBuffer collisionBuffer;
    
    void Start()
    {
        particleBuffer = new ComputeBuffer(maxParticles, ParticleStruct.Size);
        // ... инициализация данных
        simulationShader.SetBuffer(0, "Particles", particleBuffer);
    }
    
    void Update()
    {
        // Запуск ядра симуляции
        simulationShader.Dispatch(0, 
            Mathf.CeilToInt(maxParticles / 256f), 1, 1);
    }
}

// 2. Структура частицы (упакованная для эффективности)
public struct ParticleStruct
{
    public Vector3 position;      // 12 байт
    public Vector3 velocity;      // 12 байт
    public float mass;            // 4 байта
    public int type;              // 4 байта
    // Итого: 32 байта на частицу → 3.2 МБ для 100к частиц
    
    public static int Size => 
        sizeof(float) * 7 + sizeof(int); // 32
}
```

✅ Процедурные эффекты с тысячами взаимодействующих объектов
✅ Динамическая деформация среды (разрушаемый ландшафт)
✅ Исследовательские проекты, прототипы

### Когда лучше остаться на стандартной физике:
❌ Обычные игры с десятками-сотнями Rigidbody

## 🧭 БЛОК 9: FLOAT PRECISION ДЛЯ ОГРОМНЫХ МИРОВ

### Проблема в двух словах:
Тип `float` в C#/Unity — это **32-битное число с плавающей точкой** (стандарт IEEE 754). Он даёт примерно **7 значащих десятичных цифр точности**.

### Что это значит на практике:
```csharp
float a = 1000000f;
float b = a + 0.1f;
Debug.Log(a == b); // Может вернуть TRUE!
```
При координатах порядка миллиона, разница в 0.1 уже **не помещается в мантиссу** float и отбрасывается.

### Симптомы в игре:
- Персонаж «дёргается» или «телепортируется» при долгой игре
- Пули пролетают сквозь стены при определённых координатах
- Коллизии работают нестабильно на больших расстояниях от (0,0,0)
- Процедурная генерация даёт артефакты (повторяющиеся паттерны)

### Почему double не спасает:
1. **Unity внутри использует float**: `Transform.position` — это `Vector3` из трёх float. Даже если вы считаете в double, при присвоении позиции данные обрежутся.
2. **GPU работает на float**: шейдеры, рендеринг, физика — всё 32 бита.
3. **Производительность**: double занимает в 2 раза больше памяти и медленнее в вычислениях.

### Решение №1: Floating Origin (плавающее начало координат)

**Идея**: не позволять игроку уходить далеко от (0,0,0). Когда он достигает порога — сдвигаем **весь мир** обратно к нулю, а игрока — в центр.

```csharp
public class FloatingOrigin : MonoBehaviour
{
    public Transform player;
    public float resetThreshold = 1000f;
    public float resetOffset = 500f;
    
    void LateUpdate()
    {
        if (player.position.magnitude > resetThreshold)
        {
            Vector3 offset = player.position - resetOffset * player.position.normalized;
            
            // Сдвигаем ВСЕ объекты мира
            foreach (var obj in FindObjectsOfType<MovableObject>())
            {
                obj.transform.position -= offset;
            }
            
            // Возвращаем игрока в «безопасную зону»
            player.position = resetOffset * player.position.normalized;
        }
    }
}
```

**Что нужно сдвигать**:
- Все Transform с мировыми координатами
- Системы частиц (Particle System.main.startPosition)
- Навигационные сетки (NavMesh)
- Точки спавна, триггеры, зоны
- Данные процедурной генерации (если они кэшируются в мировых координатах)

### Решение №2: Локальные координаты + глобальный «сектор»

**Идея**: разбить мир на «чанки» или «сектора». Внутри каждого сектора координаты локальные (близко к 0), а глобальное положение хранится отдельно.

```csharp
public struct GlobalPosition
{
    public int sectorX, sectorY, sectorZ; // Глобальный «адрес» сектора
    public Vector3 localPosition;         // Локальные координаты внутри сектора (точность высокая)
    
    public Vector3 ToWorldVector3()
    {
        return new Vector3(
            sectorX * SECTOR_SIZE + localPosition.x,
            sectorY * SECTOR_SIZE + localPosition.y,
            sectorZ * SECTOR_SIZE + localPosition.z
        );
    }
}
```

**Преимущества**:
- Высокая точность внутри сектора
- Удобно для процедурной генерации по чанкам
- Легко сериализовать для сохранения/сети

**Сложности**:
- Нужно конвертировать координаты при переходе между секторами
- Физика и рендеринг всё равно требуют «глобальных» float-координат → нужен слой преобразования

### Решение №3: Относительные вычисления

**Идея**: не сравнивать абсолютные позиции, а работать с **относительными векторами**.

```csharp
// ❌ Плохо: сравнение абсолютных позиций
if (player.position == targetPosition) { ... }

// ✅ Хорошо: сравнение относительного расстояния
Vector3 toTarget = targetPosition - player.position;
if (toTarget.sqrMagnitude < threshold * threshold) { ... }
```

**Почему это работает**: разница двух больших чисел может быть маленькой, и при вычитании теряется меньше точности, чем при работе с каждым числом по отдельности.

### Дополнительные техники:

#### ✅ Epsilon-сравнение вместо ==
```csharp
// Никогда не делайте так:
if (a == b) { ... }

// Делайте так:
if (Mathf.Abs(a - b) < 0.0001f) { ... }
// Или встроенный метод:
if (Mathf.Approximately(a, b)) { ... }
```

#### ✅ Относительное сравнение для больших чисел
```csharp
public static bool ApproximatelyRelative(float a, float b, float tolerance = 0.0001f)
{
    float diff = Mathf.Abs(a - b);
    float maxVal = Mathf.Max(1f, Mathf.Max(Mathf.Abs(a), Mathf.Abs(b)));
    return diff <= tolerance * maxVal;
}
```

#### ✅ Фиксированный шаг для физики
```csharp
// ❌ Зависит от FPS — накопление ошибки непредсказуемо
void Update()
{
    rb.velocity += gravity * Time.deltaTime;
}

// ✅ Фиксированный шаг — ошибка накапливается предсказуемо
void FixedUpdate()
{
    rb.velocity += gravity * Time.fixedDeltaTime;
}
```

```csharp
public class AudioManager : MonoBehaviour, IAudioService
```

## 🔋 БЛОК 11: UNITY ENERGY SAVER PLUGIN — АВТОМАТИЗАЦИЯ ЭНЕРГОЭФФЕКТИВНОСТИ

### Репозиторий: [github.com/wtfoliver/UnityEnergySaver](https://github.com/wtfoliver/UnityEnergySaver)

### Суть плагина
Плагин **автоматически переключает профили производительности** игры в зависимости от активности игрока. Если игрок не взаимодействует с игрой определённое время — система снижает потребление ресурсов, экономя заряд батареи и уменьшая тепловыделение.

### Зачем это нужно в процедурном мире:
- Процедурная генерация + динамическая загрузка ассетов = высокое энергопотребление

- На мобильных устройствах и ноутбуках это напрямую влияет на время автономной работы

### Архитектура плагина: три ключевых компонента

#### 1. EnergySaver (Singleton-менеджер)
```csharp
// Основной компонент, который:
// - Слушает ввод (новый Input System или Legacy)
// - Отслеживает время бездействия
// - Переключает активный EnergyProfile
// - Применяет изменения через IEnergyActions

public class EnergySaver : MonoBehaviour
{
    [SerializeField] private float idleThreshold = 10f;
    [SerializeField] private List<EnergyProfile> profiles;
    
    // Автоматически определяет отсутствие ввода
    // и понижает профиль при превышении порога
}
```

#### 2. EnergyProfile (Настройки профиля)
Каждый профиль описывает, какие параметры изменить при активации:

| Параметр | Описание | Пример значения |
|----------|----------|----------------|
| `ActivateAfterIdle` | Время бездействия до активации | 10 секунд |
| `MaxFps` | Ограничение кадров в секунду | 30 / 60 / 120 |
| `RenderInterval` | Интервал рендеринга (каждый N-й кадр) | 1 = каждый кадр, 2 = каждый второй |
| `RenderScaleMultiplier` | Множитель разрешения рендера (для URP) | 0.5 = половина разрешения |
| `PhysicsSimulationMode` | Режим обновления физики | Fixed / Variable / Disabled |
| `Priority` | Приоритет при выборе профиля | Чем выше, тем важнее |
| `PowerConstraints` | Ограничения по питанию | Только от батареи / Только в фокусе |

#### 3. IEnergyActions (Интерфейсы действий)
Конкретные реализации, которые применяют настройки:

```csharp
// 1. FrameRateAction — ограничение FPS
public class FrameRateAction : MonoBehaviour, IEnergyAction
{
    public void ApplyProfile(EnergyProfile profile)
    {
        Application.targetFrameRate = profile.MaxFps;
    }
}

// 2. RenderingIntervalAction — рендеринг через кадр
// Полезно, когда игра не требует плавной анимации (меню, пауза, кат-сцены)
public class RenderingIntervalAction : MonoBehaviour, IEnergyAction
{
    public void ApplyProfile(EnergyProfile profile)
    {
        // Устанавливает, что новый кадр рендерится только каждый N-й тик
        // FPS при этом может оставаться высоким для логики
    }
}

// 3. PhysicsSimulationAction — управление физикой
public class PhysicsSimulationAction : MonoBehaviour, IEnergyAction
{
    public void ApplyProfile(EnergyProfile profile)
    {
        // Переключает между:
        // - Fixed Update (стандарт)
        // - Variable Update (адаптивный шаг)
        // - Disabled (полное отключение, если физика не нужна)
        Physics.autoSimulation = profile.PhysicsSimulationMode != SimulationMode.Disabled;
    }
}

// 4. RenderScaleAction (URP) — динамическое разрешение
public class RenderScaleAction : MonoBehaviour, IEnergyAction
{
    public void ApplyProfile(EnergyProfile profile)
    {
        var urpAsset = GraphicsSettings.currentRenderPipeline as UniversalRenderPipelineAsset;
        if (urpAsset != null)
        {
            urpAsset.renderScale = profile.RenderScaleMultiplier;
        }
    }
}
```

## 🤖 БЛОК 12: CLAUDE CODE + UNITY MCP — ИИ-УСКОРЕНИЕ РАЗРАБОТКИ

### Видео-туториал: [Claude Code with Unity Engine Tutorial](https://www.youtube.com/watch?v=Sknh2p12W8c)

### Что такое Claude Code + MCP?
- **Claude Code** — режим Claude от Anthropic, способный **читать, писать и исполнять код** в реальном времени
- **MCP (Model Context Protocol)** — открытый стандарт, позволяющий ИИ-моделям **безопасно взаимодействовать с внешними инструментами**, включая редакторы, API, файловые системы

### Как это применяется в Unity:

#### 1. Генерация кода по описанию
```text
Пользователь: "Создай систему пулинга для префабов врагов с поддержкой Addressables"

Claude Code:
- Генерирует класс EnemyPoolManager с методами Spawn(), Release()
- Добавляет поддержку AsyncOperationHandle для Addressables
- Пишет тестовый сценарий для проверки утечек памяти
- Предлагает оптимизации под ECS-архитектуру
```

#### 2. Рефакторинг существующего кода
```text
Пользователь: "Переделай этот MonoBehaviour на чистый C# class с DI"

Claude Code:
- Анализирует зависимости класса
- Предлагает интерфейс для каждой внешней службы
- Генерирует Composition Root для сборки графа
- Сохраняет поведение, но улучшает тестируемость
```

#### 3. Отладка и анализ ошибок
```text
Пользователь: "Почему Addressables.ReleaseInstance не выгружает память?"

Claude Code:
- Проверяет, не удерживается ли ссылка в статической коллекции
- Анализирует жизненный цикл AsyncOperationHandle
- Предлагает добавить Resources.UnloadUnusedAssets() после ReleaseInstance
- Рекомендует использовать Memory Profiler для подтверждения
```

#### 4. Документация и комментарии
```text
Пользователь: "Добавь XML-комментарии ко всем публичным методам в WorldProceduralScatterDirector"

Claude Code:
- Генерирует <summary>, <param>, <returns> для каждого метода
- Учитывает специфику процедурной генерации в описаниях
- Предлагает примеры использования в комментариях
```

#### Шаг 3: Интеграция с редактором
- Через **Unity Package Manager** устанавливается вспомогательный пакет `com.unity.mcp-bridge`
- Пакет создаёт локальный WebSocket-сервер, через который Claude получает доступ к:
  - `AssetDatabase` — метаданные ассетов
  - `EditorApplication` — управление состоянием редактора
  - `PlayerSettings` — настройки билда

### Преимущества для процедурной генерации:

✅ **Быстрое прототипирование**: «Сгенерируй шум Перлина с октавами для высоты и влажности» → готовый Burst-совместимый код

✅ **Оптимизация под платформу**: «Оптимизируй этот код под WebGL» → автоматическая замена `System.IO` на `UnityWebRequest`, удаление рефлексии

✅ **Документирование сложных систем**: «Объясни, как работает CandidateMap в моём проекте» → ИИ анализирует код и генерирует диаграмму потока данных

✅ **Поиск утечек**: «Найди все места, где создаются текстуры в runtime, но не уничтожаются» → список с ссылками на строки и рекомендациями по фиксу

### Ограничения и риски:

⚠️ **ИИ не понимает контекст проекта на 100%** — всегда проверяй сгенерированный код, особенно в критичных местах (физика, сеть, сохранение)

⚠️ **Безопасность**: не давай ИИ доступ к продакшен-серверам, ключам API, пользовательским данным

⚠️ **Зависимость от провайдера**: Claude — проприетарная модель, возможны изменения в API, тарифах, доступности

### Альтернативы и дополнения:

- **Tabnine** — локальная модель, лучше для приватных проектов
- **Unity Muse** — официальный ИИ-инструмент от Unity, но пока ограничен генерацией ассетов и анимаций

## 🧰 БОНУС: ШПАРГАЛКА ПО БЫСТРОЙ ДИАГНОСТИКЕ

### 🔍 «Игра тормозит при генерации мира»
```text
1. Открой Profiler → CPU Usage
2. Найди самый тяжёлый метод в иерархии
3. Если это твой код:
   - Проверь, нет ли аллокаций в цикле
   - Добавь [BurstCompile] и NativeArray, если возможно
4. Если это Unity internal:
   - Проверь, не генерируешь ли ты меш каждый кадр
   - Используй Mesh.CombineMeshes() заранее
```

### 🔍 «Память растёт и не падает»
```text
1. Открой Memory Profiler → Take Snapshot
2. Сравни два снимка: до и после генерации чанка
3. Ищи:
   - Текстуры/меши, которые не выгружаются
   - События, на которые подписались, но не отписались
   - Статические списки, куда добавляются, но не удаляются объекты
4. Добавь Resources.UnloadUnusedAssets() после выгрузки чанка
```

### 🔍 «Билд слишком большой»
```text
1. Открой Build Report (после сборки)
2. Сортируй по размеру
3. Ищи:
   - Неиспользуемые ассеты в Resources/
   - Дубликаты текстур (разные настройки компрессии)
   - Включённые, но не используемые модули (Physics, Video, AI)
4. Используй Addressables для выноса контента в отдельный пак
```
