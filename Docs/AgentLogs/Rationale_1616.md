# Rationale 1616 - Current Continuation

Archive note: previous 1616 rationale was moved to `Docs/Archive/Batch015/AgentLogs/Rationale_1616.md`. This file records only the live continuation after archive handover.

Problem: `H8BridgeLiveSyncScheduler` queued `IDataVault` and macro service references for one-frame `LateFrameTick` bridge flush, but it had no hot-swap listener. A DataVault or MacroDatabase replacement between request enqueue and visual sync flush could write bridge authoring data through stale services. Dispatcher replacement could also leave `s_registered=true` while the runner was absent from the new dispatcher lane.
Solution: Make the static runner implement `IGlobalRegistryHotSwapListener`. `RegisterRunnerCold` now requires both late-frame registration and hotswap registration before accepting requests. DataVault replacement clears design/input/prefab queues; MacroDatabase replacement clears design queue; Dispatcher replacement resets the runner registration flag and re-registers if any request is pending.
Rejected Alternatives: Resolving `GlobalRegistry.DataVault` inside `LateFrameTick` was rejected as hot registry polling. Keeping stale queued requests for best effort was rejected because stale bridge writes are worse than dropping a one-frame authoring sync. Adding a managed event bus was rejected because the static runner already owns the route.
Scalability potential: Low tier avoids stale bridge writes during service churn with no frame cost; middle/high/ultra keep live authoring sync phase-safe while dispatcher/service hotswaps stay deterministic.
Hardware Impact: Runtime hot-path impact 0 us. `LateFrameTick` remains `FlushLateFrame()` only; hotswap work executes only on cold service replacement and bounded fixed arrays of 32 requests per lane.

Problem: `Arm64AlignmentFaultGizmo.OnDrawGizmos` polled `GlobalRegistry.DataVault` on every editor gizmo repaint. It is editor-only, but AGENTS requires gizmos to visualize cached data and avoid live dependency searches in draw callbacks.
Solution: Cache the vault in `OnEnable`, implement `IGlobalRegistryHotSwapListener`, update the cached vault on DataVault replacement, and clear/unregister on disable/destroy. `OnDrawGizmos` now reads `_vault` only.
Rejected Alternatives: Leaving the registry read in `OnDrawGizmos` was rejected because repaint frequency is uncontrolled and it violates the cached-data visualization rule. Adding a managed editor event was rejected because the existing GlobalRegistry hot-swap lane is the correct cold dependency route.
Scalability potential: Low tier/editor laptops avoid repeated registry reads during scene view repaint; high/ultra diagnostics keep the same visual alignment marker while hotswap remains deterministic.
Hardware Impact: Runtime player impact 0 us. Editor repaint saves one static registry lookup per gizmo draw; cold lifecycle pays one lookup and one listener registration.

Problem: `GlobalRegistry.UnregisterDataVault` cleared the active vault bind for MathGuard, SignalBusRegistry, and telemetry, but it did not release the DataVault-owned handles opened by signal tuning, signal telemetry ring buffer, and signal thread-local scratchpad. If the active vault unregisters without a full `GlobalSignals.DisposeAllQueues()` shutdown, those static handles can continue to describe buffers owned by a retiring vault.
Solution: Add a narrow cold helper, `ReleaseSignalDataVaultOwnedHandles()`, and call it only when unregistering the active DataVault instance. The helper releases `SignalTuningTable`, `SignalTelemetryRingBuffer`, and `SignalThreadLocalScratchpad` handles before the registry slot is cleared.
Rejected Alternatives: Calling `GlobalSignals.DisposeAllQueues()` from `UnregisterDataVault` was rejected because it disposes every typed signal lane and resets the entire signal corridor, which is too broad for a service unregister path. Moving release into hot signal reads was rejected because read accessors must stay pure and allocation-free.
Scalability potential: Low tier avoids native-handle drift during scene unload and service churn; middle/high/ultra retain typed signal lanes across narrow vault teardown instead of paying a full signal corridor reset.
Hardware Impact: Runtime hot-path impact 0 us. Teardown cost is bounded to the three signal-owned vault handle groups and happens only during cold DataVault unregister.
