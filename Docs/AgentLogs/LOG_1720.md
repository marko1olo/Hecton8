# LOG_1720

2026-06-02

What was wrong:
- Runtime volumetric fog still carried shader-side procedural density noise.
- Cave SDF runtime path could still allocate/build/upload a Texture3D unless explicitly replaced.
- The first 1720 baker direction duplicated SDF/BVH ownership instead of extending the existing Static Cave SDF Forge.
- `HectonVolumetricParticulateFogFeature.AddRenderPasses` could reacquire DataVault through GlobalRegistry in the render loop.
- Legacy cave SDF upload held a DataVault write lock during Unity `Texture3D.SetPixelData/Apply`.

What was done:
- Added `Assets/_Project/Editor/Bakers/VolumetricTextureBaker.cs` for editor-only fog density/flow Texture3D baking.
- Packed fog as R=density, G/B=flow, A=255 with periodic Burst value-noise.
- Removed RGBA32 fallback; fog bake now emits packed RGB565 raw Texture3D payload or aborts.
- Extended `StaticCaveSdfBakePipeline` with `StaticCaveSdfTexture3DExportMode.EncodedUnorm` and `CompressSdfToEncodedByteJob`.
- Added a `writeDiagnostics` overload so the 1720 SDF route reuses Static Forge without report/self-audit I/O.
- Switched encoded SDF Texture3D output and legacy runtime fallback to R8 to match `.r` shader consumers.
- Wired `Hecton_VolumetricFog.compute` to `_HectonBakedFogDensityFlowTexture`; removed `Hash31`, `ValueNoise3`, and `Fbm3`.
- Added baked fog Texture3D binding and 256-byte frame constants to `HectonVolumetricParticulateFogFeature`.
- Added prebaked SDF bridge to `HectonCaveVoxelLightingVolume`; legacy runtime SDF generation remains disabled by default.
- Cached DataVault outside render hot paths; legacy SDF upload now copies under lock and uploads after lock release.
- Moved legacy occupancy spatial hash and SDF encode outside DataVault write locks; write locks now cover copy-only windows.

Verification:
- `git diff --check`: only CRLF warnings.
- Brace/paren/bracket balance: zero on touched C#/compute files.
- Orphan `.meta` scan: zero.
- Unity MCP `validate_script`/`read_console`: blocked by transport failure to `127.0.0.1:8088/mcp`.
- `dotnet build`: not run; latest CPU sample was 47%, but `VBCSCompiler` was active.
