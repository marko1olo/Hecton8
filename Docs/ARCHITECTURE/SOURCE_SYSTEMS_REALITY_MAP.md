## Read Rule

- Source wins over docs when a doc claims a system is absent, only planned, or already ready in runtime.
- A `.cs` file proves implementation surface only.
- `BurstCompile`, `SignalBus<T>`, `GlobalRegistry`, and `GlobalDataVault` hits do not prove runtime correctness.
- Before changing a system, open the concrete owner file and identify owner phase, dispatcher lane, signal route, DataVault buffers, failure mode, and proof artifact.

## Current Interpretation

- The project contains real implementations across most declared systems.
- `Docs/Lore` contains real AppliedContent route evidence; current scan still treats it as source-present, not level-integrated, because scene/prefab non-zero lore hash bindings remain unproven.
- Many systems are source-present but not proven in Unity runtime.
- Root-level `.cs` files remain important active owners; folder maps alone are insufficient.
- Global authority risk is concentrated in broad `GlobalRegistry` use, dispatcher lane mixing, DataVault ownership, and source-level route cards that have no runtime artifacts.
- World streaming/voxel/scatter systems are source-present and DataVault-heavy; treat them as runtime cost risks until scene wiring, save/load, profiler, VRAM, and visual capture evidence exists.
- Presentation systems are large and must be treated as runtime cost risks until Frame Debugger/profiler/GC evidence exists.
- Runtime support systems are source-present, but optimization, networking, modding, QA/headless, and build tooling each need their own proof artifacts before product-readiness claims.

## Documentation Consequence

When a system doc is updated:

- use `STATIC_SOURCE_PRESENT` for source-only state;
- cite concrete source owners, not domain labels alone;
- keep runtime status `PENDING VERIFICATION` unless fresh artifacts exist;
- never copy historical route-card status as current readiness;
- prefer this map plus `PROJECT_RUNTIME_TOPOLOGY.md` before dated reports.
