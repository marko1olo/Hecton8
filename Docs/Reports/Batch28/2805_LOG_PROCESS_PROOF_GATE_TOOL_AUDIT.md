## Required Tool Purpose

Design target:

`HectonProofPacketGate` must be a local static CLI that validates a completed proof packet folder before human review.

It must not:

- launch Unity;

- build;
- kill processes;
- delete or modify proof artifacts;
- judge visual taste from pixels;
- upgrade evidence beyond static packet-gate proof.

It must reject packets when the packet cannot prove identity, freshness, log cleanliness, route label truth, or capture isolation.

## CLI Contract

Command:

```text
python Tools/ProofGate/validate_proof_packet.py ^
  --packet-root Docs/Screenshots/HectonProofPackets/h8_1475_s01 ^
  --packet-id h8_1475 ^
  --session-id s01 ^
  --expected-quality q060 ^
  --min-post-capture-clean-seconds 60 ^
  --json-out Docs/AgentLogs/ProofPacketGate_h8_1475_s01.json ^
  --md-out Docs/AgentLogs/ProofPacketGate_h8_1475_s01.md ^
  --strict
```

Flags:

- `--packet-root`: required folder to validate.
- `--packet-id`: required packet id. Must match manifest and screenshot filenames.
- `--session-id`: required session id. Must match manifest.
- `--expected-quality`: optional `qNNN`; when provided, all production views must match it and manifest `global_quality_weight`.
- `--min-post-capture-clean-seconds`: default `60`.
- `--json-out`: optional audit JSON output.
- `--md-out`: optional audit Markdown output.
- `--strict`: fail on unknown production files, PNGs outside `screenshots/`, reused diagnostic files, or manifest fields present but empty.
- `--allow-diagnostic-view`: allow view 7 as diagnostic only. It cannot substitute for production views.
- `--forbidden-token-profile visual_proof_v1`: default token set below.

Exit codes:

- `0`: static packet gate passed. This means review may start. It is not visual acceptance.
- `1`: packet rejected by static gate.
- `2`: missing CLI input, malformed path, unreadable JSON, invalid schema.
- `3`: internal validator error.

Top-level JSON output:

```json
{
  "schema": "hecton8.proof_packet_gate.v1",
  "status": "PASS_STATIC_GATE",
  "evidenceClass": "STATIC_SOURCE",
  "maySubmitForHumanVisualReview": true,
  "mayClaimPlayerCaptureVerified": false,
  "packetRoot": "...",
  "packetId": "h8_1475",

}
```

The tool must never output `PLAYER-CAPTURE VERIFIED`. That label requires the runtime harness and human visual gate after static packet gate pass.

Implement as Python, not PowerShell.

Reason:

- Existing repo validators are mostly Python and already use the necessary primitives: `argparse`, `json`, `hashlib`, `pathlib`, `unittest`, temporary fixture roots, and deterministic exit codes.
- PNG IHDR parsing and manifest schema validation are simpler and more testable in Python.
- PowerShell is useful for guarded build/process wrappers, but this tool is file/schema/log validation, not process control.
- The tool must be unit-testable without Unity, and Python fixtures are already the local standard.

Do not implement in this 2805 pass because the task grants a single owned report path only. Implementation is clearly useful and safe in a follow-up task with write scope for `Tools/ProofGate` and tests.

## First 20 Minutes Impact

This tool removes a review-process blocker for the first-20-minutes route proof packet. It does not improve visuals, gameplay, or performance. It prevents false acceptance of screenshots that lack route truth, clean logs, and packet identity.

## Scalability Consequences

- Low: static validator runs without Unity, no GPU, no import, no build, no runtime cost.
- Middle: manifest/log/PNG validation remains deterministic and cheap enough for routine packet review.
- High: optional future perceptual checks can be added after the static gate, but must not replace manifest/log proof.
- Ultra: extra diagnostic screenshots may be validated, but production acceptance still depends on the same six required route views and clean log window.

## Strongest Blockers

1. No existing end-to-end proof packet validator exists.
2. Current screenshot conventions are contaminated by loose PNGs, `.meta` files, generic names, and old diagnostic captures.
3. Existing `h8_1474_*` six-view set lacks the required manifest in `Docs/Screenshots/MCP`.
4. Dirty-log failure modes from Batch25, Batch26, and Batch27 remain hard rejects until a clean-window validator exists.
5. Current raw screenshot tools can emit images but do not prove route, depth, quality, post-capture cleanliness, or import isolation.
6. Static validation can block false proof, but it cannot accept visual quality. Human visual review and runtime harness acceptance remain separate gates.

The validator should accept only a single manifest-bound proof packet whose six production screenshots, PNG metadata, SHA256 values, timestamps, route/depth/quality predicates, log path, and clean post-capture window all agree.
