## Decision 021 - PDA Must Fail Closed When The Physical Shell Is Missing

Problem: Static prefab evidence still shows `Player.prefab` `PlayerPDA` with null `pdaPanel`, null `pdaCanvasGroup`, and null tabs, while static scene/prefab scans did not prove `DiegeticPDAController` placement. Before R22, `PlayerPDA.Open()` could set `IsOpen=true`, switch to UI input, release the cursor, request PDA depth of field, play audio, and raise PDA events even if no visible PDA shell had configured the panel. That is a first-hour input trap risk.

Solution: Keep the existing diegetic bridge architecture but make the backend fail closed. R22 makes `PlayerPDA.Open()` require a renderable shell: non-null `pdaPanel` and at least one resolved tab. If the bridge has not configured the shell, open returns before mutating global PDA state or input maps. Input-map switches are also guarded against missing/uninitialized `GlobalRegistry.Input`. `ContentSanityValidator` now validates `Player.prefab` for `PlayerPDA` headless-open risk and exposes `PlayerPdaHeadlessOpenRisk` / `PlayerPdaBridgeWarnings` summary counters.

Rejected Alternatives: Creating a raw YAML PDA shell inside `Player.prefab` was rejected because hand-authoring a complex UI hierarchy without Unity import is corruption-prone and likely to fight concurrent UI agents. Adding another runtime auto-installer that instantiates UI was rejected because it would hide scene/prefab ownership instead of proving the physical shell. Leaving the issue documented only was rejected because a headless input lock is a player-facing failure mode.

Scalability potential: Low = on MX350, PDA open cannot capture controls into an invisible UI; missing shell is a clear validator/runtime error instead of a soft lock. Middle = editor validation makes prefab regressions visible before route tests. High = once the shell is mounted, richer PDA tabs can be measured without confusing backend state with presentation. Ultra = visual overkill should go into the physical tablet, phosphor/render-texture presentation, scanner visualization, and diegetic input after the shell route is proven.

Hardware Impact: Runtime guard runs only on PDA open/close input paths, not per frame; expected hot-path impact is 0 us/frame. Validator is editor-only. No Unity compile/import/PlayMode/profiler proof was run, so runtime cost remains PENDING VERIFICATION.

## Decision 028 - World Pager Must Fail Closed When The Page File Is Locked

Problem: Fresh Unity Console evidence after compile reconciliation no longer showed C# compiler errors, but it did show a bootstrap/runtime fault: `H8BinaryWorldPager` threw `IOException: Sharing violation on path ... world_data.h8bin`, which propagated through `SaveManager` and failed `GameBootstrapper` CoreServices with `BIOS ERROR 0xBOOT_TIMEOUT`. In a multi-editor/parallel-agent workspace, one locked persistence page file must not prevent the project from bootstrapping.

Solution: Keep the async pager and fixed-size native queues, but make initialization fail closed on file-system ownership failures. `H8BinaryWorldPager.Initialize()` now catches `IOException` and `UnauthorizedAccessException`, records an initialization fault, increments IO telemetry, emits one development warning, and leaves the pager uninitialized so write/read calls reject rather than throwing. `SaveManager` now checks `HasInitializationFault` before retrying initialization, preventing per-frame open spam. During the same pass, duplicate `SaveManager` dehydration-drain/notification methods were collapsed to the bounded route that writes voxel, inventory, and metadata payloads, and public pager APIs were returned to safe C# signatures so normal services can call them without unsafe context leakage.

Rejected Alternatives: Switching the page file to `FileShare.ReadWrite` was rejected because it hides multi-writer corruption risk. Killing the other Unity/editor process was rejected as an environmental workaround, not a product fix. Retrying the open every tick was rejected because a locked file would turn persistence into repeated IO exceptions/log spam. Treating the fault as fatal was rejected because persistence degradation is preferable to blocking bootstrap in editor/development environments.

Scalability potential: Low = on MX350 or parallel-editor machines, the game can still bootstrap when async page persistence is temporarily unavailable; chunk page IO rejects cleanly instead of stalling the boot route. Middle = save/load proof can now distinguish persistence-backend availability from global bootstrap health. High = the world pager can keep its bounded native queues and background worker when the file is available. Ultra = visual/system overkill should be bought after persistence has explicit save/load/profiler proof, not by allowing a locked disk file to take down the world.

Hardware Impact: Hot-path impact after a lock fault is 0 us/frame for open retries because `SaveManager` does not reinitialize a faulted pager. Normal initialized pager behavior remains fixed-queue/background IO; no PlayMode/profiler/GC proof was captured. Unity `6000.4.1f1` batchmode import/script compilation ran with `Library/Codex_DOC_AUDIT_UnityBatchCompile.log`; strict scan found no `error CS`, bootstrap exception, or BIOS timeout lines, and the log ended `Exiting batchmode successfully`. A later read-only Unity MCP Console readback first returned `0` errors and `7` warnings from ADB/Crest/MCP bridge/serializer surfaces; final read-only Console readback returned `0` log entries. Runtime save/load correctness remains PENDING VERIFICATION.

## Decision 029 - Async Pager Compile Clean Is Not Chunk Persistence Correctness

Problem: R29 fixed the visible compile/bootstrap layer, but static source review found deeper pager correctness issues. `H8BinaryWorldPager` still opened `world_data.h8bin` with `FileShare.ReadWrite`, directly contradicting the single-writer corruption boundary recorded in Decision 028. The pager worker needed a bounded stop handshake before native disposal; otherwise `Dispose()` could release native arenas while the worker was still alive. `TryCopyCompletedPage()` could leave ready results pinned when the destination/result was invalid. Unwritten sparse sectors and hash-collided pages were classified as corruption, causing false black-box dumps. At the integration layer, `SaveManager.EnqueueChunkDehydrationPayloads()` captured the entire global `VoxelDeltaProcessor` native snapshot for every dehydrated chunk, then wrote it as a chunk page; `WorldChunkResidencyManager` requested voxel page reads without an apply route, so ready payloads were telemetry at best, not hydration.

Solution: R30 corrected the pager from "compile-clean experimental route" toward fail-closed correctness. `world_data.h8bin` now uses `FileShare.Read`, preserving diagnostic readers while rejecting concurrent writers. The pager worker now uses `_workerStopLock`, `Monitor.Wait`, and `Monitor.PulseAll` to bound shutdown before native disposal. Invalid ready read results now release their slot/result instead of poisoning the fixed read ring. Empty headers and valid headers for a different sector/payload resolve as `Missing`, not `Corrupt`, because sparse random-access files and fixed-slot hash collisions are fallback cases, not evidence of disk corruption. `SaveManager` no longer writes global voxel snapshots on chunk dehydration; it keeps only inventory-shadow and chunk metadata sidecar writes until a real chunk-local voxel snapshot/apply contract exists. `WorldChunkResidencyManager.RequestLoad()` no longer enqueues orphaned `VoxelDeltaRle` prefetch requests.

Rejected Alternatives: Keeping `FileShare.ReadWrite` was rejected because it permits two writers to silently corrupt the same fixed-slot binary sidecar. Applying pager-ready voxel payloads inside `WorldChunkResidencyManager` was rejected because the payload currently represents a global `VoxelDeltaProcessor` snapshot, not an isolated chunk-local delta; applying it during chunk hydrate could overwrite unrelated voxel state. Writing a chunk-specific capture by guessing from `chunkId` was rejected because `VoxelDeltaProcessor.ChunkAddress` uses chunk coord and voxel size, while the streaming chunk id is AUP-derived; inventing that mapping in persistence would create another hidden cross-domain dependency. Leaving the R29 route untouched was rejected because it would turn compile success into false persistence confidence.

Scalability potential: Low = on MX350, chunk unload no longer performs a potentially large global voxel snapshot allocation/write per dehydrated chunk, and unwritten sparse pages fall back without corruption spam. Middle = page IO now has single-writer semantics and bounded result cleanup, making later save/load proof less noisy. High = a future chunk-local voxel delta contract can reuse the pager API once capture/apply semantics are real. Ultra = visual/system overkill should be bought after chunk persistence is artifact-proven; until then, saved cycles belong to stable streaming, impostors, and visible feedback, not fake hydrate telemetry.

Hardware Impact: Hot path impact is expected to improve under streaming churn because R30 removes one potentially large `Allocator.Persistent` voxel snapshot capture and 256 KB page write attempt per dehydrated chunk. Pager open/write/read hot paths remain fixed-queue/native-copy based. Shutdown cost can add up to `250 ms` bounded wait only during controlled disposal, not per frame. No Unity import, PlayMode, save/load roundtrip, profiler, GCMonitor, Memory Profiler, player build, or frame-time measurement was run in R30, so the performance numbers remain engineering estimates, not measured proof.

## Decision 030 - Pager Sidecar Must Not Be A Boot Dependency Without Runtime Proof

Problem: After R30, concurrent workspace churn reintroduced the exact bad chunk-dehydration path: `SaveManager.EnqueueChunkDehydrationPayloads()` again captured a full global `VoxelDeltaProcessor` native snapshot and labeled it `worldPagerVoxelDeltaSnapshot`. Static source also showed `InitializeNativeBuffers()` opening `world_data.h8bin` during `SaveManager.Awake()` / `InitializeService()`. That made the async sidecar pager a cold-boot dependency even when no chunk page IO had been requested, while the remaining 132 MB save-buffer residency is still unproven on low-end hardware.

Solution: R31 removes the returned global voxel snapshot block again and keeps sidecar chunk dehydration limited to inventory shadow plus chunk metadata. `InitializeNativeBuffers()` no longer calls `EnsureWorldPagerInitialized()`, so the binary pager object/file/native queues are created only when an actual chunk sidecar write/read path asks for them. The main save/load native buffers are left unchanged because lazy-loading those arenas is a larger behavioral refactor and needs PlayMode/save-load proof.

Rejected Alternatives: Full lazy allocation of the 64 MB raw save buffer and 68 MB compressed buffer was rejected in this pass because it touches core save/load timing and failure behavior without runtime proof. Guessing a chunk-local voxel mapping was rejected again because the current available snapshot is global, not a safe per-chunk payload. Running Unity, dotnet, PlayMode, profiler, or Memory Profiler was rejected under the user's machine-load constraint.

Scalability potential: Low = MX350/editor boot no longer pays a pager file-open/native-pager cost before sidecar IO is needed, and chunk unload does not serialize a global voxel blob. Middle = persistence proof can measure save-buffer residency separately from pager sidecar residency. High = chunk-local page IO can be reintroduced when capture/apply ownership is explicit. Ultra = visual overkill should be bought by stable streaming and visible feedback after persistence artifacts prove the sidecar route, not by boot-opening unused binary files.

Hardware Impact: Expected cold-boot improvement is removal of one `world_data.h8bin` open attempt plus `H8BinaryWorldPager` object/native queue/arena residency until first sidecar IO. Expected streaming improvement is again removal of one potentially large native snapshot allocation and 256 KB page-write attempt per dehydrated chunk. No Unity import, PlayMode, save/load roundtrip, profiler, GCMonitor, Memory Profiler, player build, or frame-time measurement was run in R31, so these remain engineering estimates.

## Decision 031 - Save Buffers Belong To First Persistence Use, Not Boot

Problem: R31 removed the pager file-open dependency from boot, but `SaveManager.Awake()` / `InitializeService()` still called `InitializeNativeBuffers()` and allocated the large save working set immediately: 64 MB raw payload buffer, about 68 MB compressed payload buffer, and 10 MB staging arena. That is defensible for an instant-save product only after memory evidence. Without Memory Profiler proof it is a hard low-tier boot tax.

Solution: R32 splits always-on state from working persistence buffers. Boot now initializes only the `300`-entry save telemetry ring and the `9`-entry load-candidate scratch. The raw payload, compressed payload, and staging arenas are allocated on first actual persistence use: full save gets `EnsureSaveWorkingBuffers()`, load gets the raw buffer plus candidate scratch before `_isBusy` is set, and chunk sidecar dehydration gets only the 10 MB staging arena. This preserves existing binary format and save/load pipeline ownership while removing large cold-boot residency.

Rejected Alternatives: Shrinking the save payload capacity was rejected because it changes save-format limits and needs data-size proof. Disposing the large buffers immediately after every save/load was rejected for now because repeated allocation/free during autosave churn can create stalls; persistent-after-first-use is the conservative middle step. Leaving all buffers at boot was rejected because it makes low-end boot pay for a feature that may not run during the first minutes of play.

Scalability potential: Low = toaster/MX350 boot no longer reserves the large save working set before first persistence operation. Middle = first save/load still pays a visible cold allocation burst, which can be scheduled behind UI/loading if needed. High = later Memory Profiler proof can decide whether to release buffers after use, pool them, or keep them resident for instant autosave. Ultra = high-end devices can keep resident persistence arenas after first use and spend saved boot budget on richer streaming/feedback instead of invisible preallocation.

Hardware Impact: Expected cold-boot native residency reduction is approximately 64 MB + 68 MB + 10 MB, minus tiny telemetry/candidate scratch retained at boot. First save/load/chunk-sidecar use now pays the allocation cost explicitly. No Unity import, PlayMode, save/load roundtrip, profiler, GCMonitor, Memory Profiler, player build, or frame-time measurement was run in R32, so this is static engineering evidence, not measured proof.

## Decision 032 - Lazy Allocation Must Fail Closed Before It Allocates

Problem: R32 moved large save buffers to first use, but the first-use boundaries still had two weak edges. Chunk dehydration called `EnsureWorldPagerInitialized()` and then allocated the 10 MB staging arena if `_worldPager` was merely non-null; a locked or faulted pager would reject writes anyway, so that fault path could still pay staging memory. `LoadGameAsync()` allocated the raw buffer and load-candidate scratch before entering the `try/finally`, so a NativeArray allocation failure could bypass the normal load failure reporting and `_isBusy` cleanup envelope.

Solution: R33 makes the chunk sidecar path return unless the pager exists, is initialized, and has no initialization fault before allocating `_saveStagingBuffer`. Load first-use allocation now happens inside the load `try` with `candidates` initialized to default; `ClearLoadCandidates()` already handles default/uncreated arrays safely. This keeps the lazy allocation policy but removes avoidable fault-path residency and routes allocation failure through the same load failure path as IO/format errors.

Rejected Alternatives: Allocating staging before pager readiness was rejected because it spends memory on a write path known to reject. Leaving load allocation before the `try` was rejected because low-memory failures should not skip user-visible failure state. Catching allocation separately was rejected because the existing load error envelope already records failure, raises events, hides the loading screen, and clears busy state.

Scalability potential: Low = on MX350/parallel-editor machines, a locked `world_data.h8bin` no longer triggers 10 MB staging allocation through chunk dehydration. Middle = low-memory load failures have one consistent failure path. High = later profiler proof can evaluate whether staging should release after sidecar churn. Ultra = high-end devices can still keep first-use buffers resident after successful use, but fault paths stay cheap and deterministic.

Hardware Impact: Expected fault-path native residency reduction is 10 MB when the pager cannot initialize. Load allocation failure now uses the managed failure path instead of escaping before cleanup. No Unity import, PlayMode, save/load roundtrip, profiler, GCMonitor, Memory Profiler, player build, or frame-time measurement was run in R33.

Replacing the ladder probe with a new async query contract was rejected because the existing motor already provides recent batched ladder hits. Caching negative misses permanently was rejected because dynamic scene edits/prefab changes could add a ladder component later; the cache stores only positive component resolution.

Scalability potential: Low = MX350 fixed locomotion path avoids repeated component lookup while ladder snap is active. Middle = future player-controller decomposition should start from seams with existing caches/probes, not broad rewrites. High = profiler proof can decide whether footstep material parent-provider lookup, hazard influence, and presentation signals need similar caching or extraction. Ultra = visual overkill belongs in presentation layers after fixed locomotion remains deterministic and cheap.

Hardware Impact: Expected cost reduction is small and localized: one repeated collider component lookup avoided during ladder snap reuse. No Unity import, PlayMode, ladder interaction proof, profiler, GCMonitor, player build, or frame-time measurement was run in R34.

## Decision 034 - PDA HLOD Points Need Dirty-Version Uploads, Not Repeated Fixed Buffer Writes

Problem: The `WORLD_STREAMING_LOD_MANAGER` reports correctly moved HLOD impostor residency toward native SOA and GPU-resident matrix streams, but static source review found `PDAMapTab.TryResolveHlodImpostorAupBuffer()` still uploaded its fixed `16`-point HLOD AUP buffer every map build whenever at least one impostor point existed. That is bounded, but it violates the bandwidth discipline rule: unchanged data must not be resent just because a consumer rendered another pass.

Solution: Expand `IStreamingBackpressureService` with scalar `ActiveImpostorVersion` and implement it as a separate point/read-model version in `WorldChunkResidencyManager`. `PDAMapTab` now caches uploaded HLOD version/count, clamps count to the native point array length, clears unused fixed slots only when the read model changes, and skips `GraphicsBufferUploadUtility.UploadArray` on unchanged HLOD point data. Renderer matrix dirty state remains separate from PDA point dirty state, so fade-progress point updates can advance the PDA version without forcing renderer matrix uploads.

Rejected Alternatives: Reusing `_activeImpostorVersion` directly was rejected because it is already the renderer matrix version; advancing it for PDA fade progress would reintroduce matrix uploads during transitions. Ignoring PDA `Fade01` changes was rejected because the map overlay would display stale fade state. Adding a new concrete PDA-to-world dependency was rejected because the existing `IStreamingBackpressureService` boundary is the correct read model.

Scalability potential: Low = MX350 avoids repeated unchanged fixed HLOD POI uploads while the PDA map is open. Middle = transient fade updates still publish bounded 16-point changes. High = longer HLOD range can feed PDA without increasing CPU object churn. Ultra = saved bandwidth can be spent on richer cartography/sonar presentation after runtime proof, not on resending identical overlay data.

Hardware Impact: Expected saving is one skipped `16 x float4` PDA HLOD buffer upload per unchanged map build with active distant impostors. Fade-out transitions still upload while `Fade01` changes. No Unity import, PlayMode, PDA map proof, profiler, GCMonitor, Frame Debugger, player build, or frame-time measurement was run in R35.

## Decision 035 - Recurrent Chunk Pager Voxel Writes Are A Regression, Not A Feature

Problem: Final regression grep after R35 found `worldPagerVoxelDeltaSnapshot` reintroduced in `SaveManager.EnqueueChunkDehydrationPayloads()`. That block captured the entire global `VoxelDeltaProcessor` snapshot for every dehydrated chunk and wrote it as `H8WorldPagePayloadTypes.VoxelDeltaRle`. This is the same correctness problem documented in Decisions 029 and 030: the payload is global, not chunk-local, and chunk hydration still has no safe apply contract.

Solution: Remove the recurrent block again. Chunk dehydration sidecar writes are limited to inventory shadow and `ChunkDehydratedSignal` metadata until a real chunk-local voxel delta capture/apply contract exists. The post-fix scoped grep found no `FileShare.ReadWrite`, no `worldPagerVoxelDeltaSnapshot`, and no direct `RequestAsyncPagerRead(chunkId)` in the pager integration files.

Rejected Alternatives: Keeping the write as harmless telemetry was rejected because it consumes native memory and page IO under a false chunk-local label. Applying the global snapshot during chunk hydrate was rejected because it can overwrite unrelated voxel state. Guessing a chunk-local mapping from the current chunk id was rejected because the existing snapshot API is not scoped that way.

Scalability potential: Low = MX350 streaming no longer pays a potentially large global snapshot allocation/write for each dehydrated chunk. Middle = persistence proof can focus on inventory/metadata sidecars without fake voxel success. High = a chunk-local voxel contract can be added later with explicit ownership. Ultra = saved IO/memory budget belongs to visible streaming/HLOD feedback after correctness proof, not false persistence payloads.

Hardware Impact: Expected saving is the removal of one global native voxel snapshot capture and one `VoxelDeltaRle` page write attempt per dehydrated chunk. No Unity import, PlayMode, save/load roundtrip, profiler, GCMonitor, Memory Profiler, player build, or frame-time measurement was run in R36.

## Decision 036 - Compile Evidence Must Follow The Latest Concurrent Source Snapshot

Problem: After the R36 voxel-snapshot regression guard, concurrent churn reintroduced `async void RunWorkerAsync()` / `Awaitable.BackgroundThreadAsync()` inside `H8BinaryWorldPager`. The same reconciliation pass exposed `Hecton8.Core.Memory` compile walls when `GlobalDataVault` referenced Burst/Mathematics/GlobalSignals surfaces that are not available through its Bee response-file boundary. Reporting R36 as final would have been stale.

Solution: Restore `H8BinaryWorldPager` to an explicitly owned background `Thread` with `_workerThread`, `RunWorkerLoop()`, and a `Join()`-first shutdown wait before the existing monitor fallback. Keep `GlobalDataVault` inside the `Hecton8.Core.Memory` asmdef boundary: no Burst attribute, no Unity.Mathematics rcp dependency, no `GlobalSignals`/`MemoryAddressShiftSignal` dependency. Validate with Unity Bee/Roslyn response files, using temp output/refout paths: `Hecton8.Core.Memory` exit code `0`, then `Hecton8.Core` exit code `0` with the temp Core.Memory ref.

Rejected Alternatives: Trusting the earlier successful compile was rejected because the source changed after it. Keeping `Awaitable.BackgroundThreadAsync` was rejected because the pager needs a joinable worker before native arena disposal. Adding Burst/Mathematics/Core references to `Hecton8.Core.Memory.asmdef` was rejected because it expands the lowest memory layer to satisfy a local audit helper. Claiming Unity clean was rejected because Unity MCP Console returned `no_unity_session`.

Scalability potential: Low = MX350 editor/runtime paths keep pager shutdown deterministic and avoid hidden native arena races. Middle = Core.Memory remains a small dependency island that other asmdefs can reference without pulling extra signal/math packages. High = persistence and memory audits can be measured once Unity import/PlayMode is stable. Ultra = saved engineering risk should be spent on real chunk-local persistence and visible streaming feedback after runtime proof, not on false async/background ownership.

Hardware Impact: Runtime hot-path saving is not measured. Expected risk reduction is shutdown/cold-path correctness: one joinable pager worker instead of fire-and-forget async, plus no Core.Memory dependency expansion. Local compile evidence exists; Unity import, PlayMode, profiler, GCMonitor, Memory Profiler, player build, save/load roundtrip, and frame-time measurement remain PENDING VERIFICATION.
