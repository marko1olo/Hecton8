# META_CAMPAIGN_DIRECTOR Rationale

## Intake Decision
Problem: Meta campaign logic must exist without restoring singleton architecture or string-driven quest checks.
Solution: Use GlobalRegistry contract binding, GlobalSignals queue consumption, pre-baked FNV1a uint identifiers, NativeParallelHashMap state, and Burst-compatible rule structs.
Rejected Alternatives: CampaignManager.Instance/GameManager.Instance because singleton lookup couples unrelated systems and violates local architecture mandate. String quest keys because runtime hashing/compare is allocation-prone and brittle.
Scalability potential: Low uses state-change-only toxicity/color/encounter gates. Middle adds global radio and POI deltas. High adds stronger visual overkill through shader global intensity. Ultra can add downstream renderer embellishments without changing the campaign evaluator.
Hardware Impact: i3/MX350 expected hot-frame impact near 0 us when no progression signal arrives; state shift work is cold path.

## Persistence Decision
Problem: Native campaign variables must survive save/load without managed dictionary authority.
Solution: Serialize fixed-capacity uint/int pairs in compact sorted/run-friendly arrays inside SaveData payload.
Rejected Alternatives: JSON/string mod data because it bypasses binary save ownership and adds runtime parsing.
Scalability potential: Low stores a small packed map. High/Ultra can add additional variables without changing the event evaluator contract.
Hardware Impact: Save/load work is cold path; no steady-frame cost.

## Registry Isolation Decision
Problem: Campaign logic needed a runtime owner without making Core depend directly on a new narrative assembly.
Solution: Added IMetaCampaignService to registry contracts, added a MetaCampaignRuntime registry slot, and made MetaRuntimeInstaller attach the concrete service by reflected type name.
Rejected Alternatives: Direct `CampaignManager.Instance`, direct Core assembly reference to Hecton8.Narrative.Campaign, or enemy-spawner-owned campaign state. These create dependency direction failures and refactor loops.
Scalability potential: Low/Middle query a tiny service interface. High/Ultra can add visual overkill consumers behind the same registry contract without touching spawners.
Hardware Impact: i3/MX350 pays one registry pointer read per cold encounter tick; no hot-frame lookup loop.

## Signal DAG Decision
Problem: Progression triggers must shift global world state without string comparisons or managed event chains.
Solution: Added GlobalWorldStateSignal and a Burst IJob that evaluates fixed MetaCampaignRule entries against ProgressionEventSignal using precomputed FNV1a uint hashes.
Rejected Alternatives: `Hash("ToxicityLevel")` at runtime, ScriptableObject graph walking per frame, or direct quest manager calls. These add GC risk or hidden coupling.
Scalability potential: Low handles Base Delta and Leviathan flags. Middle adds radio/cartography side effects. High/Ultra can add shader/VFX consumers that subscribe to the same state signal.
Hardware Impact: Idle cost is 0 us. On i3/MX350, a rare state-event job is expected at 10-25 us plus one late-frame apply.

## Cinematic Cheat Decision
Problem: Toxicity and late-game ocean shifts need to feel global without simulating contamination or per-biome bespoke logic.
Solution: Use `_HectonOceanToxicity` as a shader/global visual scalar and inject sparse prey-biomass pulses into safe shallows through IEcosystemDirectorService.
Rejected Alternatives: Particle/proton/voxel contamination, per-material rewrites, or full biome simulation. These spend frame time without better player-facing control.
Scalability potential: Low shows global color/toxicity and shallow depletion. Middle adds VWS and map changes. High amplifies post/underwater materials. Ultra can layer overkill visuals from the same scalar.
Hardware Impact: i3/MX350 gets one global shader set and a 2-second biomass pulse only when state changes/toxicity is active; no steady campaign simulation.

## Encounter Gate Decision
Problem: Leviathan spawns must be mathematically impossible before the story flag, regardless of stress.
Solution: EncounterDirector copies its authoring snapshot, then clamps LeviathanMaxSimultaneous and critical-health allowance to zero unless IMetaCampaignService reports Leviathan_Awakened.
Rejected Alternatives: Adding another stress branch inside the Burst job or hardcoding day thresholds. The snapshot clamp keeps the existing pacing solver intact.
Scalability potential: Low forbids apex early. Middle allows scripted awaken. High/Ultra can increase downstream spectacle after the same variable flips.
Hardware Impact: i3/MX350 cost is one service read per cold tick; the Burst job remains branch-equivalent because max simultaneous is zero.

## Blackbox And Recovery Decision
Problem: A broken quest trigger or NaN must not leave campaign state unexplained.
Solution: Maintain a fixed 300-entry NativeArray blackbox with stage hash, variable hash, value, toxicity, flags, and sequence; hidden MetaCampaignDevConsole force-sets globals through the same service path.
Rejected Alternatives: Debug.Log trails, inspector-only toggles, or manual save edits. These fail postmortem and produce inconsistent side effects.
Scalability potential: Low uses binary dump and force-set. Middle/High/Ultra can replay or visualize the same ring without touching game logic.
Hardware Impact: One 24-byte ring write per state shift; dump is crash/cold path only.

Hardware Impact: i3/MX350 normal frame impact remains 0 us when no progression signal exists. Start adds one cold service pointer refresh below 2 us. Duplicate cleanup avoids destroying unrelated root services and avoids a follow-up bootstrap rebuild.

## FIFTH FOLLOW-UP HARDENING PASS
Problem: A single `ProgressionEventSignal` can produce several variable changes, such as BaseDeltaDestroyed, ToxicityLevel, and CampaignStage. The completion loop applied and published each change immediately. Early packets therefore used a stale final campaign snapshot: BaseDelta and Toxicity signals could carry the old stage hash before CampaignStage was applied.
Solution: `CompletePendingEvaluation` now batches rule output. It applies all variable mutations first, refreshes cached campaign state once, then publishes every GlobalWorldStateSignal/VWS/cartography side effect from the final stage/toxicity values. Dev-console force-set still uses the single-change path because it is explicitly one variable.
Rejected Alternatives: Publishing per-rule immediately was rejected because packet order leaked partial state. Completing the job inside Tick and doing synchronous rule application was rejected because it violates the job mandate. Collapsing all changes into one signal was rejected because downstream systems may need the specific variable hash that changed.
Scalability potential: Low tier gets deterministic final-state packets. Middle/High/Ultra can add more rules to a progression event without producing incoherent stage/toxicity combinations; visual-overkill consumers receive final-state values.
Hardware Impact: i3/MX350 normal frames remain 0 us. A BaseDelta-style event now does one cached-state refresh instead of up to three, saving roughly 2-6 us on the cold event path and removing stale packet risk. Queue packet count is unchanged to preserve per-variable semantics.

Hardware Impact: i3/MX350 normal frames remain 0 us without progression events. Memory cost is about 512 B payload for 64 uint/int pairs plus native container overhead. ## NINTH FOLLOW-UP HARDENING PASS

Rejected Alternatives: Leaving re-enable state to a future load callback was rejected because visual publication already happens in `OnEnable`. Allowing duplicate future rule outputs was rejected because it multiplies state packets and blackbox rows. Treating dev force-set as forced re-broadcast was rejected because the hook is for repair, not audio/cartography spam.
Scalability potential: Low tier gets stable disable/re-enable behavior and no duplicate no-op repair packets. Middle/High/Ultra can add more rules targeting shared globals without increasing side-effect traffic by rule count.
Hardware Impact: i3/MX350 normal frames remain 0 us without progression events. Re-enable adds four tiny default hash repairs on a cold lifecycle path. Duplicate future rule targets now save one GlobalWorldStateSignal, one blackbox row, and any aggregated side-effect pressure per duplicate target. Repeated no-op dev force-set avoids one state signal plus side-effect pass.
