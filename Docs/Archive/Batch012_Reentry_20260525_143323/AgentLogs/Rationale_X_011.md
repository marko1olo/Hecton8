## Decision 01 - VWS Priority Word

Problem: NativeMinHeap-style scheduling is unjustified for five canonical alarms and leaves a larger mutation surface than the VWS route needs.
Solution: Replace the active alarm state with VocalWarningPriorityState.VwsPriorityWord. Warning IDs map to high bits: 1->63, 2->62, 3->61, 4->60, 5->59. Fetch uses a high-bit scan over the ulong; each bit owns one VocalWarningDTO slot, so repeated triggers coalesce by replacing only when priority score wins or extending expiration/flags.
Rejected Alternatives: Binary heap and sorted set were rejected because they require compare/sift work and more state writes for a tiny fixed domain. A FIFO queue was rejected because low-value spam could suppress critical alarms. A full 64-slot sort was rejected because bit position already encodes canonical priority.
Scalability potential: Low tier resolves the active VWS set with one word and five possible occupied slots. Middle tier keeps more producer evaluations. High tier raises evaluation cadence and distortion/spatial presentation. Ultra spends saved CPU on richer voice coloration and directional subtitles, not on scheduler complexity.
Hardware Impact: Static estimate versus heap path is removal of O(log n) sift writes and queue traversal; on i3/MX350 this should save tens of CPU operations per trigger. Measured microseconds are pending because compile/profiler execution was blocked by CPU 100% and active csc.exe.
