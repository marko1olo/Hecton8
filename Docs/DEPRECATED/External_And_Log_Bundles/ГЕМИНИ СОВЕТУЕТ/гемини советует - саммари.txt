HECTON-8 — ПОЛНАЯ ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ ДЛЯ КОДЕР-АГЕНТА
Версия: сводная. Источник: анализ чатов, дампов, рыночных данных.
Цель: имплементация, а не теория.

===================================================================
РАЗДЕЛ 1. АРХИТЕКТУРА И СТРУКТУРА ПРОЕКТА
===================================================================

FEATURE-BASED СТРУКТУРА ПАПОК (обязательный переход)
Прекратить сваливать всё в Scripts/Gameplay/ и Scripts/UI/.
Каждая новая фича живёт в своей изолированной папке.
Пример структуры:
Assets/_Project/Features/Tools/LaserCutter/ — скрипты + префабы + материалы
Assets/_Project/Features/Transport/MantaScooter/ — скрипты + префабы + материалы
Assets/_Project/Features/Base/OxygenStation/ — скрипты + префабы + материалы
Это позволяет находить все зависимости фичи за секунды.

ASSEMBLY DEFINITIONS (asmdef) — КРИТИЧНО ДЛЯ ИТЕРАЦИИ
Немедленно разбить проект на независимые сборки:
Hecton.Core.Runtime
Hecton.Gameplay.Runtime
Hecton.UI.Runtime
Hecton.WorldGen.Runtime
Hecton.Editor
Запрещено писать новый код до создания этой структуры. Без asmdef любое изменение одного файла вызывает пересборку всего проекта. После разбивки компиляция ускорится в 5-10 раз.

IDISPOSABLE — УЛЬТИМАТУМ
Каждый C#-класс, который не является MonoBehaviour и подписывается на события (Action, UnityEvent, статические шины) — обязан реализовывать IDisposable.
В методе Dispose() обязательно: отписаться от всех событий, обнулить массивы и буферы.
Вызывать Dispose() при выходе в меню и при выгрузке чанка.
Объекты для аудита: HectonBiolumManager, AcousticZoneController, PowerGrid, InventoryLogic, все системы в Hecton8.Core и Hecton8.Power.
Утечки памяти в опенворлде — это смерть проекта.

ПРИНЦИП SINGLE RESPONSIBILITY
Запрещено создавать God Objects и Manager-классы на 3000+ строк.
Разделять логику: мозг (что делать) отдельно от исполнителя (как делать).
Применение: FaunaBrain — только FSM и выбор состояния. SteeringEngine — только физика движения к цели.

SCRIPTABLEOBJECT-BASED EVENTS (вместо синглтонов)
Начать переводить связь между системами на ScriptableObject-based Architecture.
События должны жить в ассетах, а не в коде.
Инвентарь не должен знать о HectonSurvivalSystem напрямую.
Создать интерфейс IConsumableProvider. Когда игрок съедает предмет, инвентарь вызывает provider.Apply(item). Это позволит отключать систему выживания (например, в креативном режиме) без переписывания инвентаря.

ИНТЕРФЕЙС-КОНТРАКТЫ (Decoupling)
Никаких прямых ссылок между системами — только через интерфейсы.
Никаких GetComponent внутри Update() или любого Tick-метода. Это мгновенный возврат задачи на доработку.

FIELD: SERIALIZEFIELД — СТАНДАРТ ДЛЯ DATA-КЛАССОВ
Использовать конструкцию [field: SerializeField] для автосвойств.
Применять для всех Data-классов и классов статов (например, SuitData).
Сокращает объём кода, поле видно в инспекторе, доступно для чтения извне, но недоступно для записи из кода.

CUSTOM EDITOR ДЛЯ СЛОЖНЫХ СИСТЕМ
Кодер-агент должен писать Custom Editor для каждой сложной системы (например, BiomeMatrixDirector).
Настройка биомов — через ползунки в инспекторе, а не через код.

КОММЕНТАРИЙ HOW TO ADD NEW CONTENT
Каждая новая система обязана содержать блок:
// HOW TO ADD NEW CONTENT
// Пример: как добавить новый тип рыбы в 2 клика.
Без этого блока система считается незадокументированной.

===================================================================
РАЗДЕЛ 2. УПРАВЛЕНИЕ ПАМЯТЬЮ И СЕРИАЛИЗАЦИЯ
===================================================================

ЗАПРЕТ НА ДИНАМИЧЕСКИЕ КОЛЛЕКЦИИ В HOT PATH
List.Add / List.Remove вызывают фрагментацию памяти и GC.
В FaunaDirector, PowerGrid и других системах с частыми обновлениями — перейти на NativeArray или фиксированные массивы с ручным управлением индексами.
Вместо удаления элемента из списка — помечать элемент как isActive = false.
Пример: для стай рыб выделить фиксированный буфер MaxFishCount = 500.

INT-TO-STRING CACHE — ЗАПРЕТ НА .TOSTRING() В UI
Написать статический класс HectonStringCache, который при старте генерирует массив строк для чисел от -1000 до 5000.
Полностью запрещено вызывать .ToString() в UI для отображения глубины, кислорода, координат, числа ресурсов.
Использовать только HectonStringCache.Get(value).
Запрещена конкатенация строк в UI. Только StringBuilder или предзаготовленные массивы строк.

STRING CACHE ДЛЯ UI ЧИСЕЛ
StringBuilder или кеш строк — для всех числовых значений на HUD.

DETERMINISTIC GUID ДЛЯ РЕСУРСОВ МИРА
Unity InstanceID меняется при каждом запуске. Сейвы ломаются.
Каждому объекту (камень, ресурс), который спавнит WorldProceduralScatterDirector, присваивать StableHash64, вычисленный из мировых координат: Hash64(x, y, z, seed).
Это позволяет корректно сохранять состояние ("этот кусок меди собран") для бесконечного процедурного мира.

BITARRAY ДЛЯ СОСТОЯНИЯ РЕСУРСОВ
Не хранить огромные списки объектов в сейве.
Для 100 000 камней и ресурсов использовать BitArray: каждому объекту в чанке соответствует 1 бит (0 = цел, 1 = собран).
Сейв целого биома будет весить несколько килобайт вместо мегабайтов.

DELTA-SAVING (СОХРАНЕНИЕ ТОЛЬКО ИЗМЕНЕНИЙ)
Не сохранять весь мир целиком.
Сохранять только "грязные" чанки — те, где игрок что-то подобрал или построил.
Сокращает время сохранения с секунд до миллисекунд.

АТОМАРНАЯ ЗАПИСЬ СЕЙВА (ЗАЩИТА ОТ КРАША)
При записи сохранения: сначала писать во временный файл save.tmp, проверять целостность через CRC32 или MD5, только потом переименовывать в save.sav.
Это защищает игрока от потери сейва при крэше во время записи.

COMMAND BUFFER ДЛЯ СОХРАНЕНИЯ (THREAD SAFETY)
Системы не пишут в файл напрямую. Они помещают команду в очередь: SaveQueue.Enqueue(new SaveTask(data)).
Отдельный поток забирает задачи и пишет на диск асинхронно.
Это устраняет фризы при сохранении в открытом мире.

SCHEMA VERSIONING (МИГРАЦИИ СЕЙВОВ)
Игра в жанре OWSC живёт годами. Структура данных будет меняться.
Каждое изменение структуры данных (например, добавили стат "Радиация") обязано иметь класс-мигратор, который переводит старый сейв в новый формат.
Внедрить в SaveManager систему версий и миграций.

BINARY ФОРМАТ ДЛЯ БОЛЬШИХ ДАННЫХ
JSON слишком тяжёл для сохранения позиций 100 000 объектов.
Использовать Easy Save 3 в бинарном режиме для сохранения мирового состояния.
JSON оставить только для метаданных сейва (имя персонажа, скриншот, время).

CANCELLATIONTOKEN — ОБЯЗАТЕЛЕН
Все асинхронные задачи (загрузка чанков, генерация мешей) обязаны принимать CancellationToken.
Без этого возможен краш при выходе из игры, когда задача пытается обратиться к уже выгруженным объектам.

STRESS-TEST AUTO-RUNNER
Написать скрипт, который в режиме Time.timeScale = 100 заставляет игрока автоматически летать по миру, собирать и выбрасывать тысячи предметов.
Цель: убедиться, что память не "пухнет" через 10 игровых суток такого прогона.
Стабильность памяти — это маркетинговый инструмент. Игрок в OWSC проводит сотни часов. Накопленный GC-мусор через 20 часов убивает отзывы.

===================================================================
РАЗДЕЛ 3. ФИЗИКА И ДВИЖЕНИЕ
===================================================================

VELOCITY-BASED MOVEMENT (ОТКАЗ ОТ ADDFORCE)
AddForce непредсказуем для точного управления.
Для игрока и скутера использовать: rigidbody.linearVelocity = Vector3.SmoothDamp(currentVelocity, targetInput * maxSpeed, ref smoothRef, smoothTime).
Эффект: скутер плавно разгоняется и имеет длинный тормозной путь. Игрок чувствует, что толкает массу воды.

ВЯЗКОСТЬ ВОДЫ ЧЕРЕЗ SMOOTHDAMP (НЕ ЧЕРЕЗ DRAG)
Стандартный Drag в Rigidbody работает слишком грубо и одинаково по всем осям.
Вязкость реализовывать математически: currentVelocity = Vector3.Lerp(currentVelocity, targetInput * maxSpeed, deltaTime * waterResistance).
При резком повороте игрока должно немного "заносить" по инерции.

INPUT SMOOTHING
Ввод Unity (новая Input System) может быть резким (0 или 1).
Написать InputProcessor, который делает Mathf.SmoothDamp для всех осей управления (скутер, плавание).
Накапливать "волю игрока" в течение 0.05с. Управление остаётся острым, но вода сопротивляется.

RAYCAST-ПОДВЕСКА (HOVERING) ДЛЯ ТРАНСПОРТА И ШАГОХОДОВ
Скутер Manta и CrabWalker не должны касаться дна коллайдером.
Реализация: из 4 углов объекта бить лучи вниз. Сила по формуле:
F = Stiffness * (TargetDistance - HitDistance) - Damping * RelativeVelocity
Результат: транспорт плавно "облизывает" кораллы и камни, не застревает в коллизиях. Шагоход адаптируется к рельефу автоматически.

COLLISION DETECTION
Для всех быстродвижущихся объектов (торпеды, скутер, быстрые хищники) выставить Collision Detection -> Continuous Speculative.
Запрещено использовать Continuous Dynamic для массовки (слишком дорого для CPU).
Запрещено Discrete для любых снарядов.

COLLISION LAYER MATRIX — РЕВИЗИЯ
Провести полную ревизию матрицы слоёв коллизий.
Fauna не должна сталкиваться с Debris.
Loot не должен сталкиваться с Flora.
Flora (водоросли) полностью изолируется: коллизии только с Raycast игрока, ни с чем больше.
Результат: снижение нагрузки на PhysX на 30%, так как тысячи кустов перестают "проверять" столкновения друг с другом.

PHYSX CLEANUP — ОБЛОМКИ (LOOTCHUNK)
При разрушении HarvestableOutcrop спавнятся куски с Rigidbody.
Обязательно написать компонент-таймер: через 4 секунды после спавна вызывать Rigidbody.isKinematic = true и Collider.enabled = false.
Оставлять только Trigger для подбора предмета.
Океан не должен обсчитывать физику валяющегося мусора.

BUOYANCY EDGE CASE — ДЕМПИНГ У ПОВЕРХНОСТИ
Физика Unity RB при резком выходе из воды "выплёвывает" объекты с неадекватной силой.
В HectonFluidEngine внедрить Damping Zone: верхние 0.5 метра у поверхности. Сила выталкивания должна плавно затухать до нуля, а не обрываться резко.

PROCEDURAL FOOT IK ДЛЯ КРУПНЫХ СУЩЕСТВ
Использовать пакет Animation Rigging.
Для каждой лапы донного существа (краб, шагоход) пускать Raycast из колена вниз.
Если точка контакта выше/ниже таза — нога изгибается процедурно.
Лапы адаптируются к произвольному рельефу камней без ручной анимации.

PROCEDURAL LANDING DIP
Когда игрок касается дна, камера совершает процедурный "нырок" вниз и плавно возвращается.
Реализовывать не через анимацию, а через импульс в CameraJuiceProcessor.
Создаёт ощущение тяжести скафандра.

CAMERA STABILIZER
Написать скрипт CameraStabilizer, который плавно гасит микро-вибрации физического движка (Rigidbody jitter).
Применять интерполяцию позиции камеры, а не жёсткую привязку к объекту.

EXPRESSIVE PHYSICS — ВЫРАЗИТЕЛЬНЫЕ СТОЛКНОВЕНИЯ
Если игрок врезается в стену на скутере на максимальной скорости, камера должна совершать "пьяный" отскок с завалом горизонта, а не просто дрожать.
Реализовывать через CameraJuiceProcessor с передачей вектора и силы удара.
Такие "Fail Moments" — контент для соцсетей, который генерирует вишлисты.

RIGIDBODY-ИГРОК — НЕ ТРОГАТЬ
Переход на CharacterController для основного игрока запрещён на текущем этапе. Переписывать ядро HectonPlayerMovement с плавучестью, инерцией воды и интеграцией Crest Ocean — это потеря нескольких недель. Советы по CC применять только для новых механик (например, ходьба внутри базы на суше).

===================================================================
РАЗДЕЛ 4. СИСТЕМА ИСКУССТВЕННОГО ИНТЕЛЛЕКТА
===================================================================

ДВУХУРОВНЕВЫЙ ИИ (BRAIN + MOTOR)
FaunaBrain (высокий уровень) — только FSM, выбирает состояние, тикает раз в 0.5с (SlowTick).
SteeringEngine (низкий уровень) — только физика движения, плавно интерполирует поворот к цели каждый кадр.
Если ИИ-расчёт задерживается, рыба продолжает плавно плыть по инерции — визуальный слой не зависит от логического.

TIME SLICING ДЛЯ OVERLAPSPHERENONA LLOC
До перехода на Octree: жёстко разнести OverlapSphereNonAlloc у монстров по времени.
Монстры не сканируют сферу в один кадр.
Использовать: if (Time.frameCount % updateInterval == GetInstanceID() % updateInterval) — это "размазывает" нагрузку по SlowTick равномерно между всеми существами.

SPATIAL HASHING ДЛЯ ПОИСКА ЦЕЛЕЙ
Физический OverlapSphere — запрещён для массового поиска.
Использовать NativeParallelHashMap (пакет Collections) для хранения позиций рыб в пространственной сетке.
Поиск ближайшего соседа или игрока — только по соседним ячейкам хеш-таблицы.
Результат: сотни рыб, нулевая нагрузка на Main Thread.

RAYCAST BATCHING ДЛЯ "ЗРЕНИЯ" ИИ
Не пускать Raycast из Update каждого существа.
Использовать RaycastCommand.ScheduleBatch.
Раз в 0.2с система собирает все запросы "зрения" от всех существ и отправляет одним пакетом в Job System.
100 хищников проверяют видимость игрока за 0.01 мс.

FRUSTUM CULLING ДЛЯ ЗРЕНИЯ ИИ
Заменить чистый OverlapSphere на комбинацию: Distance-check + Dot Product (угол взгляда).
ИИ "видит" только то, что находится в конусе перед ним (например, 120 градусов).
Если игрок строго сзади — существо не видит его, пока игрок не начнёт шуметь.

GLOBAL NOISE BUS (ШУМОВАЯ ШИНА)
Создать статический класс NoiseManager.
Когда игрок использует лазерный резак, скутер или взрывает что-либо, он вызывает: NoiseManager.EmitNoise(position, strength).
Существа не сканируют игрока. Они подписываются на NoiseManager и реагируют на события.
Это снимает нагрузку со всех существ одновременно — вместо 500 сфер-сканеров работает 1 центральный менеджер.

RVO — ЛОКАЛЬНОЕ ОТТАЛКИВАНИЕ ДЛЯ СТАЙ
NavMesh под водой не работает.
Для стай: каждая рыба вычисляет вектор отталкивания от 3-5 ближайших соседей (из Spatial Hash) и добавляет его к направлению движения.
Это O(N) математика в SteeringEngine — работает быстрее любой физики.

IJOBPARALLELFOR ДЛЯ МЕНЕДЖЕРОВ
В исходнике явно написано: PowerGrid.UpdateBalance и аналогичные расчёты вынести в IJobParallelFor. В моём чеклисте этого нет отдельным пунктом. Это не просто оптимизация — это смена парадигмы для тяжёлых систем.


SEEDED RANDOM ДЛЯ ИНДИВИДУАЛЬНОСТИ
Использовать Unity.Mathematics.Random с сидом от GetInstanceID().
Каждая рыба получает свою уникальную амплитуду и частоту синусоиды движения хвоста.
Стая не выглядит как клоны.

HORDE MANAGEMENT (DIRECTOR AI)
Написать HectonDirectorAI.ForceSpawnHorde(position, type).
При спавне хищников строго проверять: объект должен появляться вне поля зрения игрока.
Использовать GeometryUtility.TestPlanesAABB для проверки нахождения точки спавна за пределами frustum камеры.

ЭКОСИСТЕМА С ПОСЛЕДСТВИЯМИ
Если игрок уничтожает всю мелкую фауну в радиусе километра, к базе должен приплыть голодный хищник крупнее.
Реализовывать через FaunaDirector, который отслеживает популяцию по биомам.

ВЕРТИКАЛЬНАЯ МИГРАЦИЯ (ЦИКЛ ДНЯ И НОЧИ)
Ночью крупные глубоководные существа поднимаются к поверхности, днём уходят во тьму.
Реализовывать через изменение целевых Y-координат для FSM состояния Roam в зависимости от игрового времени.
Создаёт ощущение живого океана с предсказуемой, но опасной динамикой.

===================================================================
РАЗДЕЛ 5. РЕНДЕРИНГ И ОПТИМИЗАЦИЯ
===================================================================

ОТКАЗ ОТ ТОТАЛЬНОГО STATIC
Запрещено выставлять галочку Static на процедурно генерируемых объектах.
Static Batching дублирует меши в RAM. 100 000 камней = 16 ГБ RAM. Игра не запустится.
Использовать SRP Batcher (включить в URP Asset) — он не дублирует меши, только быстро переключает данные материалов.
Проверить все префабы в _Project/Prefabs/Nature. Флаги Lightmap Static и Occluder Static должны быть выключены на всех процедурно спавнимых объектах.

TEXTURE PACKING — ЖЁСТКИЙ СТАНДАРТ (ЗАКРЕПИТЬ В PROCEDURAL_ASSET_PIPELINE.MD)
Упаковка масок в один RGBA-канал:
R = Metallic
G = Ambient Occlusion
B = Detail / Height
A = Smoothness (Gloss)
4 текстуры превращаются в 1. VRAM скажет спасибо.
Переписать все процедурные генераторы материалов и валидаторы под этот стандарт.
Написать Editor-скрипт, который автоматически берёт 4 текстуры (AO, Roughness, Metal, Height) и склеивает их в одну TexturePackerTool.
Переписать шейдеры скал и флоры под чтение этого формата.

DITHERED TRANSPARENCY — ЗАПРЕТ НА ALPHA BLENDING
Alpha Blending вызывает Overdraw. На MX350 это смерть производительности.
Перевести ВСЕ шейдеры водорослей, тумана, LOD-переходов на Dithered Alpha Clipping.
Нода Dither в Shader Graph. Режим материала — Opaque + Alpha Clip.
Полностью запрещены Transparent-шейдеры на флоре.
Внедрить паттерн Dither в Hecton_AlienSky_Master, Hecton_KelpMaster и для всех LOD-переходов.
Устранить Mat_LeakPlume и аналогичные тяжёлые полупрозрачные партикль-материалы.

DEPTH PRIMING (URP)
В настройках Forward Renderer включить Depth Priming Mode -> Forced.
Под водой много слоёв (вода, туман, водоросли) — один пиксель рисуется 5-6 раз.
Depth Pre-Pass сначала рисует только глубину, затем — только видимые пиксели.
Ожидаемый прирост: +15-20% FPS.

SHADER LOD — ДОБАВИТЬ В PROCEDURAL_ASSET_PIPELINE.MD
Обязательный раздел: Shader LOD.
На расстоянии 100м+ шейдер обязан отключать тяжёлые вычисления (SSS, сложные отражения, анизотропию).
LOD2 и LOD3 ассеты: Cast Shadows = Off. Это обязательное требование, фиксировать в документации.

SHADER KEYWORDS — ОГРАНИЧЕНИЕ
multi_compile с более чем 4 keywords даёт экспоненциальный рост вариантов шейдера и фризы при первом появлении объекта.
Проверить Hecton_KelpMaster и SG_Rock_Triplanar.
Заменить лишние keywords на static branch (if с [branch] в HLSL) или на MaterialPropertyBlock.

TRIPLANAR MAPPING ДЛЯ ПЕЩЕР
Воксельные пещеры и процедурные скалы невозможно развернуть в UV.
Весь меш пещер и скал обязан использовать World-Space Triplanar mapping.
Текстура накладывается автоматически по мировым координатам, без швов.

HEIGHT-BASED TEXTURE BLENDING
Стандартное смешивание текстур террейна — "грязный градиент".
В шейдере ландшафта реализовать смешивание по карте высот текстуры (Height Blend).
Результат: песок "засыпается" в трещины камня, а не плавно перетекает в него.
Реализм без увеличения разрешения текстур.

SCREEN SPACE CAVITY / SSAO
Добавить в URP-пайплайн SSAO или кастомный шейдер Cavity, затемняющий углубления.
Камни и кораллы выглядят гипердетализированно без добавления полигонов.

ANISOTROPY ДЛЯ МЕТАЛЛА
В шейдер визора и модулей базы добавить анизотропные блики.
Эффект: "растянутый" блик создаёт ощущение дорогого влажного металла.

DETAIL MAPS (МИКРО-ДЕТАЛИЗАЦИЯ)
В шейдер базы и шлема добавить поддержку Detail Maps (второй слой мелких текстур царапин, пыли).
Detail Map тайлится в 10 раз чаще основной текстуры.
Вблизи база выглядит гипердетализированно при текстуре основы 512x512.

VERTEX ANIMATION ДЛЯ МАССОВКИ РЫБ
Запрещено использовать Animator или кости для мелкой фауны (планктон, медузы, мелкие рыбы).
Только Shader Graph / HLSL: изгиб тела через sin(_Time.y * speed + WorldPos.x * frequency).
Каждая рыба берёт свою фазу синусоиды из seeded random по ObjectPosition.
Результат: 1000 рыб = 1 Draw Call, 0% нагрузки на CPU.

PROP WASH EFFECT (РЕАКЦИЯ ФЛОРЫ НА ИГРОКА)
В HectonUnderwaterVisuals транслировать позицию и скорость игрока в глобальные переменные шейдера: _PlayerPos, _PlayerVelocity.
В шейдерах Kelp и Coral добавить Vertex Offset в сторону от _PlayerPos, масштабированный скоростью.
Результат: водоросли пригибаются при проплывании мимо. 0% нагрузки на CPU, 100% к ощущению живого мира.

CAUSTICS — ДЕШЁВЫЙ СПОСОБ
Не использовать Projectors.
В шейдер террейна (SG_Rock_Triplanar) добавить аддитивную маску с анимированной текстурой каустики, привязанной к мировым координатам по оси Y.
Солнечные блики на дне — бесплатны по производительности.

FAKE VOLUMETRIC RAYS
Не использовать честный волюметрик свет.
Использовать меши-конусы с шейдером, который плавно затухает по Depth Buffer и Fresnel.
Шейдер обязан использовать Soft Depth Blending — не рисовать поверх игрока и объектов.

FAKE REFLECTIONS (SSR FALLBACK)
Честные отражения воды убивают FPS.
Использовать Reflection Probes с разрешением 128px и сильным блюром в шейдере.
Игроку под водой важно "чувство света", а не чёткое зеркало.

CAMERA-SPACE PARTICLES (МОРСКОЙ СНЕГ)
Не делать глобальную систему частиц на весь мир.
Навесить систему частиц ("морской снег", пыль, планктон) непосредственно на MainCamera.
Частицы спавнятся только в конусе видимости игрока.
Результат: эффект везде, физически считается 200 частиц вместо 20 000.

STENCIL BUFFER ДЛЯ СКАНЕРА РЕСУРСОВ
Для целевых ресурсов (медь, титан) добавить второй Pass в шейдер, пишущий в Stencil Buffer.
Сканер игрока активирует Post-Processing слой, который рисует контур объекта, если тот помечен в Stencil.
Ресурс за кустом или скалой даёт видимый контур.

NATIVE SVG ДЛЯ ИКОНОК (Unity 6.3+)
Иконки инвентаря, ресурсов и UI-элементы переводить в нативный SVG-формат.
Текстуры иконок в 4K съедают 200-400 МБ VRAM. Вектор съедает 2-3 МБ.
Для новых иконок инвентаря использовать вектор или жёсткие текстурные атласы.

RUNTIME ATLAS PACKING ДЛЯ МЕЛКОГО ЛУТА
Написать систему авто-атласинга для иконок инвентаря и мелких ресурсов (медь, титан, обломки).
50 видов ресурсов — один текстурный атлас, один инстансированный материал, один Draw Call.

BUILD STRIPPING
Использовать com.unity.web.stripping-tool перед сборкой демки.
Вырезать неиспользуемые модули: Physics 2D, старый UI, WebGL-специфичные компоненты.
Цель: размер билда менее 500 МБ.

РАЗДЕЛЕНИЕ CANVAS НА СТАТИЧЕСКИЙ И ДИНАМИЧЕСКИЙ

HIT FLASH ПРИ ДОБЫЧЕ (LASERCUT HIT RESPONSE)

2. Отлетающие искры (усилить существующие, увеличить импульс).
3. Лёгкий импульс в CameraJuiceProcessor при успешном раскалывании.

GLOBAL FEEDBACK MANAGER (HITSTOP)

HitStop(float duration) — заморозка Time.timeScale на 0.02-0.05с.
CameraImpulse(Vector3 direction, float strength) — резкий толчок через CameraJuiceProcessor.
ChromaticAberrationPunch(float intensity, float duration) — кратковременная вспышка искажения цвета через Post-Processing.
Вызывать при: добыче руды, ударе монстра, взрыве, критическом событии.
Это делает геймплей "сочным" на видео и генерирует контент для соцсетей.

RAGDOLL ПРИ СМЕРТИ ОТ КРУПНОГО СУЩЕСТВА

Это контент для TikTok и виральный материал.

CINEMATIC INTRO HANDSHAKE
При запуске новой игры: камера плавно "влетает" в шлем игрока через Cinemachine.
HUD включается поэтапно со звуком загрузки систем скафандра.
Первые 10 секунд игры продают качество продукта до начала геймплея.

RENDER TEXTURE ДЛЯ МОНИТОРОВ БАЗЫ

TELEMETRY (АНОНИМНАЯ АНАЛИТИКА)

LOW-PASS FILTER ПО ГЛУБИНЕ
Связать AudioMixer с SurvivalSystem.Depth.
Чем глубже игрок, тем ниже Cutoff Frequency на мастер-шине.
Звуки становятся глухими и давящими. Эффект давления воды без единой анимации.

OCCLUSION ЧЕРЕЗ RAYCAST
В SpatialAudioManager: пускать Raycast от камеры до источника звука.
Если луч заблокирован геометрией — вешать на AudioSource LowPassFilter.
Игрок слышит монстра за стеной пещеры приглушённо. При выходе монстра из-за стены — звук резко открывается.

ADAPTIVE SOUND POOLING
Не использовать PlayClipAtPoint.
Создать компонент SoundEmitter с пулом источников.
Если в радиусе 50м спавнится 20 одинаковых рыб — проигрывать звук только 3-4 ближайшим.
Предотвращает "белый шум" из сотни одновременных звуков.

ADAPTIVE SAMPLE RATE
Все фоновые звуки (гул воды, пузырьки, фоновая атмосфера) импортировать с Sample Rate = 22050 Hz.
На слабом железе это разгружает шину памяти. Под водой игрок не услышит разницы из-за Low-Pass фильтров.

ОСТАНОВКА ГОРИЗОНТАЛЬНОГО МАСШТАБИРОВАНИЯ — ПРИКАЗ
Запрещено добавлять новые системы, новые инструменты, новые типы пещер, усложнять матрицу биомов.
Текущее состояние: у нас 108 биомов, генераторы флоры, сложный ИИ. Играть невозможно.
Мы строим "движок", а не "игру".

VERTICAL SLICE
Сформировать один рабочий участок: SedimentResources с переходом в RiftHazard.
Полный микро-цикл:
Игрок спавнится -> Запас O2 падает -> Находит кусок трубы -> Режет лазером -> Получает титан -> Плывёт к фабрикатору -> Крафтит улучшенный баллон -> Плывёт глубже -> Находит первую аудиозапись с лором.
Только когда этот 15-минутный цикл играется физически приятно и без запинок — продолжаем генерировать мир.
Не рефакторить менеджеры. Собрать из готовых кусков (Inventory, Fabricator, SurvivalSystem, LaserCutter) единую непрерывную сцену.

ПРАВИЛО 30 СЕКУНД (POI PLACEMENT)
Игрок каждые 30 секунд должен видеть что-то интересное.
В WorldProceduralScatterDirector добавить проверку плотности: если в радиусе 100м нет ни одного интересного объекта (руины, редкий ресурс, пещера, арка, обломки, светящийся коралл) — система принудительно спавнит POI.
Игрок всегда должен видеть следующую цель в пределах тумана (видимость 60-100м).

МЯГКИЙ ОНБОРДИНГ (ПЕРВЫЕ 15 МИНУТ)
Если игрок умирает от нехватки кислорода в первые 5 минут — он делает рефанд.
Первые 15 минут: кислорода в избытке или база очень близко.
Дать игроку "влюбиться" в визуал и атмосферу до начала настоящего давления механик выживания.

DEMO-МАРШРУТ (15 МИНУТ IMPACT)
Структура демки:
Начало: поломка корабля, мелководье, сбор первых ресурсов.
Кульминация: спуск во тьму, включение фонаря, встреча с гигантским биомеханическим силуэтом, который просто проплывает мимо — показываем масштаб.
Конец: обрыв на самом интересном моменте.
Написать компонент DemoLimiter, обрывающий игру в нужной точке.

THE HOOK — ГЛАВНЫЙ КОЗЫРЬ ДЛЯ ТРЕЙЛЕРА
HectonDirectorAI и Atlas-6 — это уникальный продающий элемент (аналог режиссёра Left 4 Dead).
Игрок должен физически чувствовать: океан живой и наблюдает за ним, дроны Атласа заняты своими делами независимо от игрока.
Всю разработку ближайшего месяца подчинить этому ощущению. Это козырь для трейлера, который зацепит алгоритмы Steam.

СУБМАРИНА КАК "ТЫСЯЧЕЛЕТНИЙ СОКОЛ"
Игрок 80% времени должен проводить внутри, а не снаружи.
Разделить субмарину на отсеки с независимой логикой.
Система пробоин: вода физически заполняет отсек, меняет массу и плавучесть корабля.
Давление и глубина влияют на скорость работы механизмов, громкость скрипа корпуса.
Саспенс: глубина 2 км, корпус трещит, вода прибывает, нужно заварить пробоину до достижения критического давления.

СИСТЕМА ЭЛЕКТРИКИ И ЖИЗНЕОБЕСПЕЧЕНИЯ
Трубы для кислорода, кабели для энергии, фильтры для воды — физическая инфраструктура базы.
Реализовывать проще, чем в Stationeers, но с реальными последствиями: забитый фильтр = удушье.
Это увеличивает среднее время сессии в 10 раз.

ИЛЛЮЗИЯ ВЫБОРА ВМЕСТО 100 КОНЦОВОК
Не делать 100 ветвей сюжета. Сделать одну проработанную концовку, в которой учитываются 3-4 ключевых решения игрока (например, судьба ИИ Атлас-6).

SHOW, DON'T TELL
Не писать текст "здесь опасно".
Бросить пустой батискаф со следами когтей.
Вести игрока светом и геометрией, а не указателями.

ПРИНЦИП 80/20
20% механик (плавание, добыча, крафт) дают 80% геймплея.
Вылизывать их. Не тратить время на кастомизацию кроватей и декоративные механики.
