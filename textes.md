# textes.md - Public Writing Rules

Status: root writing authority for public copy.

Use this file before writing advertising copy, social posts, profile bios, store text, trailer captions, creator outreach blurbs, community replies, or any public-facing text for Teni Games / Submerge.

This is not a lore bible and not a campaign document. This is the rule set for making the text sound like a real developer instead of a content machine.

Route note: game-world text, missions, logs, and evidence use `narrative.md`. Public marketing text, store copy, social posts, creator outreach, community replies, captions, and profile text use this file. If public copy references visuals, performance, platforms, demo state, Steam status, mechanics, or release scope, `quality.md` evidence rules also apply.

## 1. Prime Rule

Write like a developer showing one real thing he is currently fighting with.

Do not write like:

- a brand manager
- a fake indie studio with a hype calendar
- a trailer voice-over
- a generic AI marketing assistant
- a press release without assets
- a fan account pretending the game already has a community

Good public text answers at least one concrete question:

- What is physically happening?
- What can break?
- What can the player choose?
- Why does the return route look bad?
- What does the machine do?
- What did the build make clearer today?

If the text needs hype to work, the asset or thought is not ready.

## 2. Default Language

Public Teni Games / Submerge copy is English by default.

Russian is allowed for internal planning, owner chat, private notes, and task files. Do not post Russian from official channels unless the owner explicitly asks for that specific post.

Japanese text is visual identity only unless native-reviewed. `天衣` is the primary visual motif. `天意` can be used as a secondary motif. Do not pretend kanji makes the studio Japanese.

## 3. Speaker

Default public speaker:

- quiet developer account
- small studio shell
- specific build/process notes
- no fake crowd

Allowed:

- `I` when the post is clearly a dev note
- `we` only when speaking as Teni Games account infrastructure or studio identity
- short fragments
- plain admissions that something is not ready yet
- dry confidence based on proof

Avoid:

- pretending the team is larger than it is
- pretending the game has traction
- pretending every post is an announcement
- explaining internal legal/account gates in public

## 4. Evidence Boundary

Never make a public claim that the current project cannot prove.

Forbidden until proven:

- demo available
- Steam page live
- wishlist now
- release window
- playable soon
- optimized for low-end hardware
- Steam Deck ready
- co-op, multiplayer, VR, console, or platform support
- realistic ocean simulation
- real physics simulation
- screenshots from gameplay if the image is only brand art
- trailer if it is only a logo loop
- official press kit if it has no proof assets

Public copy can say:

- `Submerge is in development.`
- `The account is quiet until the build can carry the image.`
- `This is profile art, not gameplay.`
- `Still building the first shots worth showing.`

But do not over-explain gates. Keep public text short.

## 5. What Submerge Text Should Sell

Do not sell "an ocean game".

Sell:

- pressure
- machinery
- salvage
- black water
- bad return paths
- weak light
- dirty glass
- hatches, seals, pumps, cables, gauges
- instruments the player has to trust
- the cost of choosing a route
- evidence left after something went wrong

The core public promise is not "beautiful underwater world".

The core public promise is:

The player is inside failing machinery under pressure, trying to make a readable decision before the way back gets worse.

## 6. Words That Usually Work

Use these when they match the asset:

- pressure
- salvage
- machinery
- black water
- return route
- bad way back
- pump
- hatch
- seal
- cable
- gauge
- sonar
- silt
- hull
- dirty glass
- low light
- repair
- route
- signal
- leak
- weight
- depth
- instrument
- trace
- failure
- evidence

Do not force them into every post. One concrete noun is better than five theme words.

## 7. Words And Patterns To Kill

Hard ban unless quoting someone else:

- `We are excited to announce`
- `Stay tuned`
- `Coming soon`
- `Embark on a journey`
- `Dive into an immersive experience`
- `A unique blend of`
- `Next-gen`
- `Revolutionary`
- `AAA-quality`
- `Cinematic experience`
- `Unparalleled`
- `Game-changing`
- `Breathtaking`
- `Beautiful and terrifying`
- `Wishlist now`
- `Subnautica killer`
- `Inspired by the classics`
- `For fans of`
- `Our passionate team`
- `We can't wait to share more`
- `The world of Submerge awaits`

Also kill:

- hashtag piles
- platform boilerplate copied everywhere
- fake questions like `Who else loves deep sea horror?`
- lore dumps before a visual hook exists
- corporate apologies
- big claims with no artifact
- public mention of internal gates like `no demo claim`, `HOLD`, `G0`, `proof pack`

## 8. Sentence Mechanics

Keep sentences short.

One post should usually contain one idea.

Prefer:

- one concrete fact
- one detail
- one restraint
- no CTA

Avoid:

- multiple clauses stacked to sound important
- explaining what the player should feel
- adjectives doing the work of evidence
- long setup before the actual point

If a sentence has three adjectives, delete two.

If a post has two CTAs, delete both.

If a post sounds like it could be about any underwater game, rewrite it.

## 9. The Human Dev Formula

Use this when stuck:

1. What did I touch today?
2. What looked wrong?
3. What is the player supposed to read from it?
4. What still needs work?

Example structure:

```text
Spent the day on [thing].
[Specific problem] was too clean / too readable / too fake.
Better now, but [remaining ugly detail].
```

Good:

```text
Spent the day on pump rooms.
The first version looked like a clean sci-fi hallway, which is useless for Submerge.
It reads better once the return path looks like something you might lose.
```

Too polished:

```text
We are crafting immersive industrial environments that challenge players to survive the crushing depths.
```

## 10. Before A Screenshot Exists

No fake launch energy.

Before real current-build screenshots, post rarely and only if the post has a reason.

Allowed topics:

- account identity
- small dev process notes
- what a good screenshot must prove
- profile art clearly labeled as profile art
- quiet build notes

Not allowed:

- launch-style announcements
- "follow for updates" spam
- daily filler
- countdowns
- wishlist requests
- "first look soon"
- fake community questions

Better:

```text
Still cutting screenshots that look good and explain nothing.
Submerge needs the machinery, the pressure, and the bad way back in the same frame.
```

Worse:

```text
Teni Games / 天衣

Studio account is being wired. Submerge is the game.

No Steam link yet. No demo claim. First public image has to explain pressure, machinery, and the bad way back without a paragraph under it.
```

Why worse:

- sounds like an internal checklist leaked into public
- says what not to claim instead of saying a human thought
- uses brand setup language nobody cares about
- reads like an AI trying to be honest

Rewrite:

```text
Opened the account before the good shots are ready.
For now I am mostly deleting frames that look cool and say nothing.
```

Another rewrite:

```text
Submerge is not ready for a clean screenshot yet.
The shot only works when the route back looks like a problem.
```

## 11. With A Screenshot

The image should do most of the work.

Caption recipe:

- name the thing in the image
- name one problem
- do not explain the whole game

Good:

```text
Pump room pass.
Too readable last week. Better now that the useful path and the bad path are almost the same color.
```

Good:

```text
The gauge is not decoration.
If it is calm, the room is lying to you.
```

Bad:

```text
Experience the tension of the abyss in our latest atmospheric environment screenshot.
```

## 12. With A Clip

The clip should show a change, not just a pretty camera move.

Good clip captions:

```text
Door timing pass.
The delay matters more than the animation.
```

```text
The cable looked fine until it started moving.
Now it feels like something the room depends on.
```

Bad clip captions:

```text
A glimpse into the haunting world we are building.
```

## 13. Platform Rules

### X / Twitter

Use 1 to 3 lines.

No hashtag pile. No thread unless there is proof.

Good:

```text
Today was mostly pumps, doors, and making black water readable without making it friendly.
```

Good:

```text
The ocean is not the hook.
The machine failing under it is.
```

### Bluesky

Can be slightly more conversational than X.

Good:

```text
Still figuring out how dirty the image can get before the player stops reading it.
Submerge needs ugly, not muddy.
```

### Instagram

Use only with real visual material or clean brand assets.

Caption should not explain the whole game.

Good:

```text
Profile art for Teni Games.
Not gameplay. Just the account getting dressed before the real shots are worth posting.
```

### YouTube

Titles must say what the viewer sees.

Good titles:

- `Submerge - Pump Room Door Timing Test`
- `Submerge - Black Water Readability Pass`
- `Submerge - Salvage Tool Audio Test`

Bad titles:

- `A New Abyss Awaits`
- `The Depths Are Calling`
- `Official Teaser`

Do not call something a trailer unless it is a trailer.

### Reddit

Always behave like a developer, not a marketer.

Disclose context.

Do not drop a sales post into a subreddit without reading rules.

Good:

```text
I am building Submerge, a pressure/machinery salvage game. This is not a trailer, just a readability test. I am trying to make the useful route and the risky route visible without color-coding the room like UI.
```

Bad:

```text
Check out our upcoming deep sea survival game!
```

### Telegram

Use as a quiet dev log / owner-side channel, not a hype feed.

Good:

```text
Cut another nice-looking shot today. It did not explain the decision, so it dies.
```

### Steam

Steam text must be factual and controlled.

Never write Steam copy like social copy.

Steam page needs:

- what the player does
- what the core loop is
- what the player risks
- what is currently in scope
- what is not promised

No insecure jokes. No internal process talk.

## 14. Bios

Bio should be short and physical.

Good Teni bio:

```text
Making Submerge. Pressure, salvage, ugly machinery, black water.
```

Good game bio:

```text
Submerge is a pressure and salvage game about machinery, bad routes, and getting back alive.
```

Too much:

```text
Teni Games is an independent studio crafting atmospheric deep-sea experiences with immersive systems and cinematic storytelling.
```

## 15. Replies

Replies should be normal.

Do:

- answer the actual question
- admit what is not ready
- avoid over-promising
- thank people plainly when needed
- move support/account issues to a proper channel once one exists

Do not:

- argue title comparisons
- attack similar games
- fake humility
- say `we are listening` unless there is a real plan to act
- turn every reply into a pitch

Good:

```text
No demo yet. I do not want to put a bad first slice in front of people just to have a link.
```

Good:

```text
Not trying to sell it as ocean realism. The important part is whether the player can read the machine under pressure.
```

## 16. Creator Outreach Voice

Creator outreach must be direct and low-pressure.

Good:

```text
Hi. I am building Submerge, a pressure/machinery salvage game.

No Steam page yet, so I am not asking for coverage. I am putting together the first proof pack and looking for channels that care about readable systems, industrial horror, and bad decisions under pressure.

If this is your lane, I can send a short private build note when the first clip is actually worth your time.
```

Bad:

```text
We would be thrilled to collaborate with you on bringing our unique underwater adventure to your amazing audience.
```

## 17. Store Copy Voice

Store copy can be more structured, but it must stay plain.

Opening line should answer:

- what is the game?
- what does the player do?
- what is the pressure?

Good:

```text
Submerge is a pressure and salvage game about keeping broken machinery alive long enough to get back.
```

Better when proven with assets:

```text
Route flooded. Pump unstable. Tool battery low. The job is still possible, but the way back is now part of the cost.
```

Bad:

```text
Submerge invites players into a haunting underwater odyssey where mystery, survival, and discovery collide.
```

## 18. The Repair Pass

If a draft sounds fake, do this:

1. Delete the first sentence.
2. Delete all adjectives that are not physical.
3. Replace feelings with visible facts.
4. Replace `we are excited` with what changed in the build.
5. Replace `immersive` with the specific object doing the work.
6. Remove CTA unless the destination exists and is worth sending people to.

Example:

Bad:

```text
We are excited to reveal a haunting new look at the world of Submerge.
```

Repair:

```text
New room pass.
The old version looked expensive and said nothing. This one at least tells you where the mistake is.
```

## 19. Truth Boundary

Public text does not create project truth. It reports only what the current build, proof asset, public page, or owner-approved plan can support.

Public copy must never:

- upgrade an internal prototype into a shipped feature;
- call a capture gameplay unless it is gameplay;
- call a render a screenshot unless it is an engine screenshot;
- imply a demo, Steam page, release window, platform target, optimization state, or creator program exists before it exists;
- turn mood, concept art, or aspirational design into a promise.

When a claim touches performance, platform, visual quality, gameplay scope, or release readiness, attach the proof source internally before publication. If the proof source is missing, rewrite the sentence until it only says what is true.

## 20. GlobalQualityWeight And Public Claim Scaling

`GlobalQualityWeight` may change how much visual detail appears in a capture, but it must not change what public text claims. A Compact capture can support statements about readability, restraint, and survival pressure. A High or Ultra capture can support statements about richer lighting, materials, particles, and presentation only when the capture is current and labeled.

Public copy must never use high-tier overkill to imply compact-tier performance, gameplay scope, platform readiness, demo availability, or release state. If a sentence says or implies "realistic", "AAA", "optimized", "VR", "Steam-ready", "demo", "release", or "multiplayer", the proof artifact must exist and be named in the internal review packet.

## 21. Proof Artifacts

Public text going out for review must identify:

- target channel;
- attached asset or proof source;
- exact claim being made;
- unsupported claims removed;
- call to action, or explicit reason there is no call to action;
- language/region target;
- owner approval state if it mentions demo, Steam, build access, pricing, release, platform, or creator outreach.

Copy without an asset or concrete observed fact is allowed only for profile/bio housekeeping. Marketing claims without proof are rejected.

## 22. Public Text Rejection Gates

Reject the draft if:

- it sounds like a trailer voice-over;
- it says `immersive`, `haunting`, `unique`, `AAA`, `realistic`, or `next-gen` without a physical fact doing the work;
- it sells mood instead of a player-readable decision;
- it claims readiness without a current proof asset;
- it compares the game to competitors as a shortcut;
- it uses internal ambition as public fact;
- it uses public hype to compensate for weak screenshots or weak footage.

## 23. Acceptance Sentence

Public text is accepted only when it is short, factual, asset-backed, physically specific, free of unsupported readiness claims, and readable as a developer showing one real problem or one real proof point instead of a campaign deck.

## 24. Final Publish Checklist

Before any public text goes out, answer:

- Does this sound like a person wrote it?
- Does it name one concrete thing?
- Does it avoid fake progress?
- Does it avoid unsupported Steam/demo/release claims?
- Does it avoid generic underwater-game language?
- Does it match the asset attached?
- Would this still be acceptable in six months?
- Can a stranger understand what the player might do next?

If two answers are no, do not publish.

## 25. The One-Line Rule

When unsure, write the ugly true version first.

Then make it cleaner, not bigger.

Good Submerge text should feel like a dev note with a pulse, not a campaign deck with a thesaurus.
