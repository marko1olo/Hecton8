# HECTON-8 XR, VR, And Comfort Bible

Status: AUTHORING LAW / STATIC DOC / RUNTIME PROOF NOT IMPLIED
Evidence class: STATIC_DOC
Scope: PCVR, standalone XR, Quest/PICO readiness, VR comfort, XR input, foveation, stencil masking, cockpit/visor UI, motion sickness, and XR proof gates.

## First-20 Route Hook

- First-20 moment: XR groundwork must preserve the same boot, world load, shallow exit, swim/orient, tool, hazard, save/load route while adding comfort, input, and per-eye readability constraints.
- Route blocker removed: XR package presence treated as proof, flat HUD copied into stereo view, foveation/stencil claims without device evidence, and XR branches changing gameplay truth.
- Proof class: `STATIC_DOC` until headset launch, frame pacing/profiler, input binding, UI readability, stencil/foveation capability, thermal/memory, and save/load artifacts exist.

## Prime Law

XR is a separate proof lane, not a high-end graphics preset.

HECTON-8 may support XR only when comfort, input, UI readability, frame pacing, thermal behavior, and platform proof exist. XR must intensify embodied pressure without making controls unreadable or nausea the primary threat. Claims about VR, Quest, PICO, or foveation are rejected without device artifacts.

User vision lock: XR/VR groundwork is a real goal and may be prepared in parallel. It remains a proof lane, not a readiness claim. Do not block flat-screen production on XR, and do not claim XR-ready without headset/device artifacts.

## Truth Ownership

XR owns headset/camera rig presentation, per-eye UI readability, comfort filters, XR input mapping, foveation/stencil paths, and XR-specific proof. It does not own gameplay truth, platform readiness, input semantics, or UI state.

`platform.md` owns platform proof ladder. `input.md` owns action semantics. `ui.md` owns interface truth. XR consumes those and adds device-specific constraints.

## Comfort Law

Required:

- stable frame pacing;
- no uncontrolled camera shake;
- comfort options for snap/smooth turning;
- seated/standing decision;
- cockpit/visor UI legibility;
- safe motion transitions;
- foveation capability check;
- stencil/fragment rejection proof where visor/HUD overdraw matters;
- thermal proof on standalone devices.

XR must never make critical UI dependent on tiny text, edge-of-eye information, or post effects that shimmer.

## XR Interaction

XR interactions must respect physical affordances:

- hand/controller rays map to diegetic panels;
- grabbing uses stable anchors and ownership;
- tool operation preserves the same action semantics as flat mode;
- haptics are cause-based and device-safe;
- cockpit controls do not require impossible body poses;
- accessibility alternatives remain available.

## GlobalQualityWeight Scaling

`GlobalQualityWeight` may scale eye buffer resolution, foveation strength, stencil regions, particle density, shadow count, UI material richness, and diagnostic overlays. It must not change gameplay truth, input semantics, UI command model, save identity, or platform claim proof.

Compact XR keeps comfort, stable UI, few particles, simple lighting, and hard load-shed. High/Ultra XR add richer cockpit/visor/material detail only after frame pacing and comfort are proven.

## Production Packet

Any XR or VR implementation must declare:

- headset/runtime/provider target;
- target frame pacing and reprojection policy;
- foveation, stencil, render scale, and MSAA route;
- input binding and locomotion comfort mode;
- UI carrier strategy for cockpit, visor, wrist, terminal, or world panel;
- motion, shake, flashing, vignette, and comfort limits;
- Compact/standalone fallback and High/PCVR visual lane;
- device launch proof for any platform claim;
- profiler/GC/GPU proof when runtime XR code or render passes change.

No document or report may claim XR readiness from desktop screenshots, static docs, or non-headset Play Mode.

## Proof Artifacts

XR work must provide:

- target headset/provider;
- player build or device launch proof;
- frame pacing/profiler proof;
- input binding proof;
- UI readability capture;
- comfort setting list;
- foveation/stencil capability proof if claimed;
- thermal/memory proof for standalone devices;
- explicit `PENDING VERIFICATION` for untested XR targets.

## Rejection Gates

Reject:

- XR readiness from package presence;
- headset claims without device launch;
- motion sickness risk hidden by "immersive";
- flat HUD copied into XR without legibility proof;
- foveation/VRS without capability check;
- stencil path without Frame Debugger/GPU proof;
- XR changing gameplay truth or save identity.

## Acceptance Sentence

XR is accepted only when device artifacts prove comfort, input, UI readability, frame pacing, thermal/memory behavior, and unchanged gameplay truth on the claimed target.
